## 1. KPI 계산 정확성

### 통과
- (a) 가동률 = RUN/(전체−PM), 분모<=0 → null (`KpiTotals.java:34-37`). 실호출 확인: PM 구간만큼 분모에서 빠짐(OVEN-01 WEEK).
- (b) MTBF = ΣRUN/downCount, 0회 null (`KpiTotals.java:40`).
- (c) MTTR = 완료 DOWN 평균, 이탈 후 상태 무관(`KpiCalculator.java:90-97`: state==DOWN에서 다른 상태로 전이 시 무조건 완료 집계), 진행 중 제외(루프 밖 `addSpan`만 호출).
- (d) 기간: `KpiPeriod.startAt` — KST 자정 `atStartOfDay(KST)` 후 `previousOrSame(MONDAY)`/`withDayOfMonth(1)` → `toInstant()`. Asia/Seoul은 서머타임 없음(1988년 이후)이라 24h/9h 고정. 실호출: 2026-10-03(토) DAY start=`2026-10-02T15:00:00Z`, WEEK start=`2026-09-27T15:00:00Z`(월 9/28 00:00 KST), MONTH start=`2026-09-30T15:00:00Z`(10/1 00:00 KST) 모두 정확. UTC 날짜가 다른 케이스는 KpiCalculatorTest(00:30 KST=전날 15:30Z, 23:59 KST=14:59Z)와 KpiPeriodTest가 커버.
- (e) 합산 재계산: `EquipmentKpiService.java:69-73` 에서 `KpiTotals.plus` 후 `Summary.of(sum)`. 실호출 WEEK summary MTBF 96.51 = ΣRUN(386.03h)/4 — 비율 평균(83.5)이 아님을 손계산으로 확인.
- (f) 경계 해석 8가지 상호 일관성: 코드·docs/03·docs/12·테스트 3자가 일치(동시각 로그=입력순 마지막, 시작 전 불명 제외, 진행 중 DOWN downCount·MTBF 포함/MTTR 제외, 시작 전 진입 DOWN downCount 제외+MTTR 절삭 포함).
  - 시작 전 진입 DOWN이 downCount에서 빠지는 것과 MTBF 분모에서 빠지는 것은 **일관적**: 그 DOWN 앞의 RUN 시간도 기간 밖이라 분자에 없다. 왜곡 없음.
  - MTBF 분모(진입 전부, 진행 중 포함)와 MTTR 분모(완료만)는 **서로 다른 DOWN 집합**이지만 스펙에 명시된 의도. 단, 아래 K-1 참조(화면에서 오해 소지).
- 쿼리: `findTransitionsInPeriod`(start<changedAt<end, `order by changedAt, id`), `findStateAtPeriodStart`(설비별 `max(changedAt)<=start` 상관 서브쿼리, 동률 시 전부 반환 + `order by changedAt, id` → 서비스가 시작 쿼리 결과를 먼저 add, 계산기의 stable sort가 id 순서 보존 → 마지막 id가 시작 상태). 다른 설비 로그는 `l2.equipment.id = l.equipment.id` 상관으로 격리, 설비 ID 목록은 `Equipment` 조회(@SQLRestriction)에서 나오므로 soft delete 설비 제외. 로그 테이블 자체는 추가 전용(soft delete 대상 아님, 엔티티 주석 명시).
- 쿼리 수: 설비 수와 무관하게 상수(설비 1 + 라인 exists 1 + 로그 2). N+1 없음. 인덱스 `idx_status_log_equipment_changed(equipment_id, changed_at)` 사용 → docs/15 PF-4/§5와 충돌 없음.

### 손계산 검증 (실DB 로그 vs 실호출, 2026-10-03T11:47:31Z 시점)

(참고: 실제 수리는 25h44m=1544.35분이고 WEEK 값 1544.35와 일치. DAY는 절삭 길이로 표시됨 → K-1.)

**계산 2 — AOI-01(id=5) WEEK.** 시작 `09-27T15:00Z`, 시작 상태 RUN(#25). 기간 내: #26 RUN→IDLE 10-01T09:05:21.32Z, #27 IDLE→DOWN 09:05:31.88, #28 DOWN→PM 09:10:53.81, #29 PM→IDLE 09:10:57.87, #30 IDLE→DOWN 09:11:08.02, #35 DOWN→RUN 10-03T11:47:30.40.

- downCount = 2(#27, #30), 완료 DOWN: 321.92s(5.365분) + 50h36m22.38s(3036.373분) → MTTR = 1520.869 → **1520.87**

**계산 3 — WEEK summary(전 설비).** ΣRUN = 90.0895(AOI) + 90.3368(LAMI-01) + 115.0526(LAMI-02) + 90.5527(OVEN) + 0.0002(SCRB) = 386.03h, Σ downCount = 2+1+1+0+0 = 4 → MTBF 96.508 → **96.51**(실호출 96.51). ### 결함/지적
- **K-1 (MED, 의미/UX)** `KpiCalculator.java:64-67`, `KpiTotals.java:40`, `KpiTiles.tsx:40` — 기간 시작 전에 진입해 기간 끝까지 DOWN인 설비(예: 야간조에 고장 → 주간 DAY 조회)는 `downCount=0, mtbf=null("고장 없음"), mttr=null, availability=0.0` → 화면에 "MTBF 고장 없음 / DOWN 횟수 0회 / 가동률 0.0%"로 나온다(실제로는 DOWN 지속 중). 또 기간 전 진입·기간 내 이탈 건은 DOWN 횟수 0회인데 MTTR만 값이 있다(실호출 실제 사례: AOI-01/LAMI-02 DAY → `downCount 0, mttrMin 1247.51`, 실제 수리 시간은 1544.35분이라 MTTR이 절삭 길이로 과소 표시됨). 스펙 의도라 계산은 맞지만 사용자가 모순으로 읽는다. 제안: ① 응답에 `ongoingDown: boolean`(시작 시점 또는 현재 DOWN 여부)·`completedDownCount` 추가 후 타일 힌트에 "기간 이전부터 DOWN 지속 중" 표시, 또는 ② 최소한 MTTR 힌트에 "기간 시작 전 진입 건은 기간 내 구간만 반영"을 명시(현재 힌트는 "진행 중 제외"만 있음). 스펙을 바꾸지 않는 선에서 UI 문구만으로도 완화 가능.
- **K-2 (LOW)** `KpiCalculator.java:49-52` — `changedAt == start`인 DOWN 진입 로그는 "시작 시점 상태"로 처리되어 downCount에서 빠진다(기간은 [start,end) 포함인데 정확히 start의 진입은 기간 내 진입으로 세지 않음). 테스트 `동시각_로그_마지막이_상태`가 이 동작을 고정. 실무 영향은 ms 단위 우연뿐이라 LOW. 스펙 문장("시작 시각 이하 마지막 로그")과 일치하므로 문서에 "정각 진입은 시작 상태로 본다" 한 줄 추가 권장.
- **K-3 (LOW)** BM(DOWN)을 PM 상태에서 수행하면(DOWN→PM 'BM 착수', 실DB 이력에 다수) PM 시간이 가동률 분모에서 빠져 가동률이 높게 나온다. 스펙(KPI-4/KPI-10)대로 구현된 것이라 코드 결함은 아님. docs/03에 "BM 작업을 PM 상태로 기록하면 가동률 과대" 주의 한 줄을 권장.
- **K-4 (LOW)** `KpiRound.java:25` 반올림: MTBF/MTTR 소수 2자리, 가동률 4자리. 아주 작은 값은 `0.0`으로 사라져 의미가 바뀐다(예: MTBF 0.004h → 0.0 → 화면 "0시간", `downCount>0`과 함께 보임). 가동률은 `9.0E-4` 같은 과학표기 JSON이 나온다(유효한 JSON이고 `JSON.parse`로 0.0009 정상 파싱 확인) — 문제 없음.
- **K-5 (LOW)** `KpiPeriod`/서비스 — 자정 00:00:00.000 정각 조회는 start==now → 빈 결과(`!start.isBefore(end)`). 테스트·문서에 "빈 기간"으로 명시돼 있어 의도됨. 새벽 00:00~00:01에는 값이 거의 의미 없다는 점만 인지.

## 3. 프론트 동작

### 통과
- 기간/라인 변경 시 이전 값 비움: `useKpiQuery`의 effect 의존성 `[fetcher, refreshMs, reloadKey]`, fetcher는 `useCallback([equipmentId|period|lineId])` → 변경 시 `loadInitial`이 `setData(null)`+로딩. 이전 effect cleanup에서 `alive=false`+`abort()`로 오래된 응답이 새 기간 값을 덮어쓰지 못함(경쟁 상태 방어 OK).
- 1분 주기 조용한 갱신(로딩 표시 없음), 실패 시 `.catch(() => {})`로 직전 값 유지, 성공 시 error 해제. 탭 숨김 중 interval 건너뜀 + visibilitychange 시 즉시 1회 갱신. 언마운트 시 abort/clearInterval/removeEventListener 정리.
- `KpiTiles`: availability null은 '-'(muted), 0.0은 '0.0%'(muted 아님)로 구분. `isKpiEmpty`(availability null + downCount 0)이면 `EmptyState`를 보여 'MTBF 고장 없음'으로 오해되지 않음(EquipmentKpiCard:46, LineKpiSection:56).
- `formatMttr` 경계(코드 추적): 0<x<1 → '1분 미만', 1 → '1분', 59.5 → 반올림 60 → `formatDuration`이 `hours=1, rest=0` → '1시간'(60분 표기 버그 없음), 1247.51 → '20시간 48분', 0 → '0분'. `formatAvailability` 0.873 → '87.3%'.
- 기간 표기: `KST ${formatKst(start)} ~ 현재` (`formatKpiRange`, Intl `Asia/Seoul`). 서버 end가 now에서 2분 이내면 '현재', 갱신이 2분 넘게 끊기면 실제 종료 시각 표기(견고).
- 'DOWN (BM)': `KpiTiles`/`LineKpiSection` 모두 `statusLabel('DOWN')` 사용. 하드코딩 색 0건(kpi.css는 `var(--border|--status-run|--status-down|--text-secondary|--bg-*|--accent)`만; `#hex`/`rgb()` grep 0건).
- 접근성: 기간 토글 `role=group`+`aria-pressed`, 접이식 `aria-expanded`/`aria-controls`, 타일 `role=group aria-label="가동률 87.3%"`. 
- AppLayout Outlet context: 라우터는 `<Routes>`+`<Route element={<AppLayout/>}>` 구조(createBrowserRouter 아님)이고 `DashboardPage`는 AppLayout 하위 index 라우트이므로 `useOutletContext` 안전. 다른 페이지는 `useOutletContext`를 쓰지 않아 영향 없음. AppLayout은 lineId 변경 때만 리렌더되어 context 객체 신규 생성 빈도 낮음.

## 4. 시뮬레이터

### 통과
- plateau 수식: `ScenarioValueCalculator.applyDrift` = `value + slope × min(elapsed, max)`, elapsed<=0 변형 없음, max<=0이면 상한 없음. `SimulatorSensorDataSource.driftMaxElapsedSeconds`: `maxElapsedSec` 우선, 없으면 `durationMin×60`, 둘 다 없으면 0(상한 없음).
- 과거 시나리오 호환: `maxElapsedSec` 없는 구 시나리오도 `durationMin×60` 상한 적용(`SimulatorSensorDataSourceTest.과거_시나리오_호환`). 실DB 현재 활성 시나리오 1건(id=4, LAMI-01 VIBRATION DRIFT, `{durationMin:2,slopePerSec:0.025,maxElapsedSec:120,targetValue:5.0}`)은 신규 포맷 — 영향 없음. 구 포맷이 남아 있으면 이미 `durationMin` 경과한 시나리오는 즉시 plateau로 바뀌는 동작 변화가 있으나 의도된 안전장치(무한 상승 방지).
- 데모 duration: `SimulatorProperties`(record, `@ConfigurationPropertiesScan`로 등록)가 null/0 이하 → 2로 보정(`:19-21`), `application.yml:64` 환경변수 `SIMULATOR_DEMO_DURATION_MIN` 기본 2, docs/13 환경변수 표에 반영. startDemo는 이미 DRIFT 활성이면 주입 안 함(`ScenarioServiceDemoTest.이미_주입돼_있으면_유지`). 수동 주입 기본 10분 유지: `ScenarioParams.DEFAULT_DURATION_MIN=10` ↔ 프론트 `DEFAULT_SCENARIO_PARAM.DRIFT.durationMin=10` 일치. 기울기 직접 지정 시 `targetValue = base + slope×maxElapsed`로 저장(crit과 무관) — 일관.

### 데모 '2분 내 자동 DOWN' 보장 여부 — 수치 분석
시드(`LocalDataSeeder.java:165`): LAMI-01 VIBRATION base 2.0, σ 0.3, warn_high 3.5, crit_high 5.0. 데모 DRIFT: duration 2분 → slope 0.025/초, **목표값 = crit_high 정확히 5.0**, 판정은 `ThresholdEvaluator`의 **엄격 초과(>)**, 값은 2자리 HALF_UP 반올림 후 판정, 판정은 샘플 1회(연속 N회 조건 없음), 샘플 주기 2초.
- ramp 구간 평균 μ(t)=2.0+0.025t. 센서값 반올림 후 `>5.00` ⇔ 원값 ≥ 5.005. P(CRITICAL | t) = 1−Φ((5.005−μ(t))/0.3).
  t=100s μ=4.5 → 4.8%, t=110 μ=4.75 → 20%, t=118 μ=4.95 → 43%, plateau(t≥120) → **49.3%**(매 샘플).
- 120초까지 60샘플 중 1회 이상 CRITICAL 확률 = **95.7%**(LAMI-01), 150초 → ≈100%(1−10^-n 수준). 다른 진동 센서(LAMI-02 96.5%, SCRB 98.3%, AOI 96.2%, OVEN 95.5%)도 비슷.
- 결론: 문서/UI 문구 "약 2분 내"는 95~96% 확률로 맞고, "3분 시연 안"은 사실상 100%. **결정적 보장은 아니다**(약 4%는 2분을 몇 초~수십 초 넘김). 또한 `target == crit`이라 σ=0인 센서(또는 σ가 매우 작은 센서)는 plateau에서 값이 정확히 crit 5.00 → "경계값은 정상" 규칙으로 **영원히 NORMAL/WARNING에 머문다** — `SimulatorSensorDataSourceTest.상한_전후`(σ=0)가 바로 이 값 5.0을 정상 값으로 검증하고 있어 "plateau=CRITICAL"을 증명하지 못한다.
- **S-1 (MED)** `ScenarioParams.java:51/resolveDriftTarget` — DRIFT 목표값이 crit_high와 정확히 같아 plateau에서 CRITICAL이 매 샘플 약 50% 확률로 깜빡이고(CRITICAL↔WARNING 플랩), σ=0 센서는 CRITICAL에 도달하지 못한다. 시연 신뢰도를 높이려면 목표값을 임계치 바깥으로 약간 둔다: 예) `target = crit_high + k·σ`(k=1 → plateau CRITICAL 확률 84%, 120초 내 도달 ≥99%) 또는 `crit×1.02`. 그러면 docs/03의 "crit 도달" 문구는 "crit 초과 목표"로 정정. 최소한 데모(`startDemo`) 경로만이라도 목표를 crit 위로 두는 옵션을 고려.
- **S-2 (LOW)** 상태 연쇄 가정: 자동 DOWN은 설비가 RUN/IDLE일 때만(`autoDown`의 `canTransitionTo(DOWN)` 검사) — 데모 시작 시 대상 설비가 DOWN/PM이면 CRITICAL이 나도 DOWN 전이가 없고(로그에 "자동 DOWN 생략"), 복귀 후 시나리오를 해제하지 않으면 plateau가 계속 CRITICAL을 만들어 재 DOWN 루프가 가능. UI 힌트에 "대상 설비가 RUN일 때"를 명시하고, 데모 초기화 시 활성 DRIFT 해제를 보장할 것.
- **S-3 (LOW)** `ScenarioService.java:startDemo` — 같은 센서에 구 DRIFT(예: 10분, 이미 plateau)가 활성이면 "이미 주입됨"으로 판단해 새 2분 DRIFT를 걸지 않는다 → 즉시 plateau 값에서 시작(타이밍 연출 상실). 활성 DRIFT의 `startedAt`이 상한을 넘겼으면 교체하는 방안 검토.
- **S-4 (LOW)** `ScenarioParams.normalizeDrift` — `durationMin<=0` 입력은 `maxElapsedSec=1`로 보정되어 즉시 목표값으로 점프(`slope=(target-base)/1`). 요청 DTO 검증(`@Min(1)`)이 없으면 의도치 않은 입력이 통과 — 기존에도 같은 문제였으나 plateau로 고정되어 영향이 커짐. `ScenarioCreateRequest`/컨트롤러에서 durationMin 범위 검증 권장.
- **S-5 (LOW, 문서/UI 드리프트)** `DemoControlPanel.tsx:191` "약 2분 내…"가 하드코딩인데 서버 설정(`SIMULATOR_DEMO_DURATION_MIN`)으로 바뀔 수 있음. 응답 param의 `durationMin`을 읽어 표시하거나 문구를 "설정된 시간(기본 2분)"으로. 프론트 `ScenarioParam` 타입에 응답 필드 `slopePerSec/maxElapsedSec/targetValue`가 없음(선택 필드라 런타임 문제 없음).
