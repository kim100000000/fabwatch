## 통과

### 경계면 — API 응답 shape ↔ 프론트 타입
- `GET /equipments` — 백엔드 `PageResponse<EquipmentSummaryResponse>` ↔ `fetchEquipments` 가 `PageResponse<EquipmentSummary>` 로 받고 `useEquipmentList` 가 `data?.content` 로 unwrap. `totalElements/totalPages/number` 3개 필드 모두 소비됨.
- `GET /equipments/{id}` — `EquipmentDetailResponse` ↔ `EquipmentDetail` 필드명 일치(id/code/name/status/processId/processName/lineId/lineName/installedAt/managerName). 백엔드가 추가로 보내는 `note/createdAt/updatedAt/managerId` 는 프론트 타입에 없지만 초과 필드라 런타임 무해.
- `GET /equipments/{id}` 미구현 하위 객체(`sensors`, `pmSchedule`, `openAlarmCount`)는 프론트에서 전부 optional + `?? 0` / `?? '-'` 폴백 처리 → 백엔드가 안 보내도 크래시 없음. `EquipmentInfoPanel.tsx:11,38,42` 확인.
- `GET /equipments/{id}/status-logs` — `PageResponse<EquipmentStatusLogResponse>` (프론트 소비자 없음, 아래 "미검증" 참조).
- `POST /auth/login` — `{accessToken, refreshToken, accessTokenExpiresIn, user{id,name,role}}` ↔ `LoginResponse`. 프론트가 `accessTokenExpiresIn` 을 안 쓰는 것은 초과 필드라 무해.
- snake_case(DB) → camelCase(API) → camelCase(프론트) 전 구간 일관. DB 컬럼명이 API로 새어나온 곳 없음(`modelName`/`installedAt`/`managerId` 등 전부 camelCase).

### 상태 머신 (docs/03 F-2)
- `EquipmentStatus.java:36-41` 전이표가 F-2 표와 **정확히 일치**: RUN→{IDLE,DOWN,PM} / IDLE→{RUN,DOWN,PM} / DOWN→{PM} / PM→{IDLE}. 무단 전이 0건, 죽은 전이 0건.
- 상태 변경 지점 전수 검색 결과 `Equipment.changeStatus()` **단 한 곳**뿐이며 `EquipmentStatus.canTransitionTo()` 를 반드시 통과. 상태 필드를 우회로 바꾸는 코드 없음.
- 보수적 거부(동일 상태 전환, PM→RUN 등 표에 없는 전이) — F-2 표와 **충돌 없음**. 표에 정의되지 않은 전이를 거부하는 것은 안전한 기본값이며, 동일 상태 거부는 상태 로그가 KPI(MTBF/MTTR) 원천이라는 근거가 코드 주석에 명시되어 있음.
- `EquipmentStatusMachineTest.java` 가 4×4 전이 매트릭스 전체 + 자기 전이 4건 + PM→IDLE 강제 흐름을 검증. 단위 테스트 존재·통과.
- 프론트 상태 분기(`EQUIPMENT_STATUSES = ['RUN','IDLE','DOWN','PM']`)의 4개 값 모두 백엔드 enum에 실재하며 도달 가능.

### 컨벤션
- soft delete: 물리 삭제 호출(`deleteById`/`deleteAll`) **0건**. 모든 소프트삭제 대상 엔티티에 `@SQLDelete` + `@SQLRestriction("deleted_at IS NULL")` 선언됨.
- 에러 포맷: 모든 에러가 `GlobalExceptionHandler` 경유 `{code, message, timestamp}`. 컨트롤러가 직접 `ResponseEntity.badRequest()` 등으로 즉흥 에러를 만드는 곳 없음. 인증 실패(`RestAuthenticationEntryPoint`)·권한 실패(`RestAccessDeniedHandler`)도 동일 포맷. 스모크 테스트가 401/403/400 세 케이스의 `code`·`timestamp` 를 실제 검증.
- 역할명: 코드/타입 어디에도 role 문자열 `MAINTENANCE` 없음. `Role.java`, `features/auth/types.ts` 모두 `ADMIN/ENGINEER/TECHNICIAN`. (등장하는 "MAINTENANCE"는 전부 "바꾸지 말라"는 주석.)
- 프론트 에러 분기가 `ApiError.code` 기준(`errorMessage.ts`). message 문자열 매칭 없음.
- 시각: 백엔드 `Instant`(UTC) 저장·응답, 프론트 `datetime.ts` 가 `Asia/Seoul` 로 표시 변환. 교대 판정 D=08~20 / N=20~08 (KST) 일치.
- `// TENANT:` 주석이 users/lines/equipments 계열 엔티티·레포지토리 6곳에 존재.
- 실설비 물리 제어(PLC/Modbus 쓰기, 인터락 실구현) 코드 **없음**. 관련 grep 히트는 "물리 제어가 아니다"라는 범위 한정 주석 2건뿐 → 에스컬레이션 불필요.
- 시드 값 전부 가상(`CELL-1라인`, `LAMI/SCRB/AOI` 코드, 고정 seed `Random(20260807L)`). 실제 LG디스플레이 공정 수치·알람 코드 흔적 없음.
- 비밀정보: 하드코딩 API 키 없음. `SEED_PASSWORD = "fabwatch123"` 은 `@Profile("local")` + `fabwatch.seed.enabled=true` 이중 게이트가 걸린 시연용 시드 계정이라 위반 아님. JWT secret / CORS origin은 `JwtProperties`·`CorsProperties` 로 외부 주입.
- CORS `allowedOrigins` 에 `*` 없음(환경변수 주입), `allowCredentials=false`.

## 실패 (수정함)

### 1. `GET /lines` 페이지 래핑 unwrap 누락 — **런타임 크래시급**
`frontend/src/features/equipment/api/equipmentApi.ts:35-38` — 백엔드 `LineController.java:21` 이 `PageResponse<LineTreeResponse>`(`{content,...}`)를 반환하는데 프론트는 `LineTree[]` 배열을 직접 기대. `useLineTree` → `Header.tsx:34` 의 `lines.map(...)` 에서 **`lines.map is not a function` 으로 헤더 전체가 터짐**(로그인 직후 모든 화면에 영향). 이 페이지 래핑은 `docs/06` 목록 공통 규칙이며 `SeedAndApiSmokeTest.java:44` 가 `$.content` 를 이미 검증 중 → 백엔드가 옳고 프론트가 틀림.
→ **수정**: `fetchLines` 의 응답 타입을 `PageResponse<LineTree>` 로 바꾸고 `data.content` 를 반환. 훅/컴포넌트 시그니처(`LineTree[]`)는 그대로 유지.

### 2. 세션 복구를 JWT 클레임 디코딩으로 하던 것 → refresh 응답의 `user` 사용
`frontend/src/app/providers/AuthProvider.tsx:78-87`(구) — "리프레시 응답에 user 가 없을 수 있어" 라는 잘못된 가정으로 Access 토큰을 직접 base64 디코딩. 실제로는 `AuthService.issueTokens()` 가 login/refresh **공통**으로 `user{id,name,role}` 을 내려준다(`TokenResponse.java:7-11`). 클레임 디코딩은 동작은 하지만(=`JwtTokenProvider.java:38-48` 이 `name`/`role` 클레임을 실제로 넣고 있음) 불필요한 우회이고, 클레임 이름이 바뀌면 조용히 `'사용자'`/`'TECHNICIAN'` 으로 폴백해 **권한 표시가 틀린 채 화면이 뜨는** 위험이 있었음.
→ **수정**:
  - `shared/api/types.ts` 에 `AuthUserSummary{id,name,role:string}` 추가 (shared→features 역참조 금지 원칙 때문에 role 은 넓은 string, 좁히기는 features/auth 에서).
  - `shared/api/client.ts` — `RefreshResponse` 에 `user`/`accessTokenExpiresIn` 반영, `refreshAccessToken()`·`restoreSession()` 반환 타입을 `RefreshResult{accessToken, user}` 로 변경. 401 인터셉터는 `.accessToken` 만 사용(동작 불변).
  - `AuthProvider.tsx` — `restoreSession()` 결과의 `user` 를 그대로 세션에 반영. 복구 실패 시 토큰도 정리하도록 보강.
  - 이제 아무도 참조하지 않는 `shared/lib/jwt.ts` **삭제**.
  - 회귀 가드: `SeedAndApiSmokeTest.리프레시_응답에_user_포함` 추가 (`$.user.name`/`$.user.role` 검증).

### 3. `POST /auth/logout` 에 불필요한 요청 바디 전송
`frontend/src/features/auth/api/authApi.ts:21`(구) — `{refreshToken}` 바디를 보냈으나 `AuthController.java:37-41` 의 `logout()` 은 파라미터가 없고 `SecurityUtils.currentUserId()`(=Authorization 헤더의 principal)로 대상 사용자를 찾아 DB Refresh 를 지운다. 바디는 서버가 무시하므로 즉시 장애는 아니지만, 계약에 없는 값(그것도 Refresh 토큰)을 네트워크에 실어 보내는 것은 불필요한 노출.
→ **수정**: `apiClient.post('/auth/logout')` — 바디 없이 호출. 회귀 가드로 `SeedAndApiSmokeTest.로그아웃_바디_없음` 추가(바디 없이 204 → 이후 해당 Refresh 는 401 `INVALID_TOKEN`).

### 4. 목록 응답에 `modelName`/`maker` 누락 — UI 컬럼이 영구히 "-"
`backend/.../dto/EquipmentSummaryResponse.java` — `EquipmentTable.tsx:43-44` 가 "모델"/"제조사" 컬럼을 렌더하고 프론트 타입도 `modelName?`/`maker?` 를 갖고 있는데 목록 DTO에 두 필드가 없었음. optional 처리 덕에 크래시는 없지만 **두 컬럼이 항상 `-`** 로 표시됨. 모델명·제조사는 docs/03 F-2 의 설비 필드이고 상세 DTO에는 이미 있음 → 목록 DTO 쪽 누락으로 판단.
→ **수정**: `EquipmentSummaryResponse` 에 `modelName`, `maker` 추가(`from()` 매핑 포함). 라인 트리 응답도 같은 DTO를 쓰므로 함께 채워짐. 회귀 가드로 스모크 테스트에 `$.content[0].modelName/maker` 존재 검증 추가.

### 5. 에러 코드 매핑이 백엔드 `ErrorCode` enum 과 불일치
`frontend/src/shared/lib/errorMessage.ts:16`(구) — 백엔드가 **발생시키지 않는** `EQUIPMENT_NOT_FOUND` 를 매핑하고 있었고(설비 404는 공통 `NOT_FOUND` 로 나감), 실제로 발생하는 `INVALID_TOKEN`/`UNAUTHORIZED`/`DUPLICATE_EQUIPMENT_CODE`/`INTERNAL_ERROR` 는 매핑 없음.
→ **수정**: 죽은 코드 `EQUIPMENT_NOT_FOUND` 제거, 위 4개 추가. `NOT_FOUND`/`VALIDATION_ERROR` 는 백엔드가 더 구체적인 message(예: "설비를 찾을 수 없습니다: id=99", 필드별 검증 사유)를 보내므로 **의도적으로 매핑하지 않고** 서버 message 폴백을 유지(주석 명시).

## 미검증 (확인 불가 / 범위 밖 / 차기 라운드)

- **구현됐지만 프론트 소비자가 없는 엔드포인트 4개** — `POST /equipments`, `PUT /equipments/{id}`, `PATCH /equipments/{id}/status`, `GET /equipments/{id}/status-logs`. 프론트 S-2에 설비 등록/수정 폼이 없고 S-3의 "상태 변경" 버튼은 `EquipmentDetailPage.tsx:39` 에서 `disabled` 상태. docs/04 S-2가 "설비 목록/**마스터 관리**", S-3이 "상태 변경 버튼(권한별)"을 요구하므로 **F-2 프론트가 미완**이다. 누락이 아니라 일정상 차기 라운드 이월로 보이나, 리더 확인 필요 — 백엔드는 이미 완성이라 프론트 화면만 붙이면 됨.
- **런타임 통합 검증 미실시** — 실제 서버를 띄우고 브라우저에서 로그인→새로고침→라인 선택 플로우를 확인하지 못함(MySQL 미기동). 결함 1·2·3의 수정은 코드 대조 + 백엔드 스모크 테스트로만 검증. 특히 새로고침 세션 복구 경로는 E2E로 1회 확인 권장.
- **프론트 테스트 러너 부재** — `frontend/package.json` 에 test 스크립트가 없어 unwrap/세션 복구 로직에 프론트 측 회귀 테스트를 남기지 못함. 백엔드 스모크 테스트가 응답 shape을 고정하는 것으로 대체.
- **`GET /equipments/{id}` 의 sensors / pmSchedule / openAlarmCount** — docs/06 상세 스펙에 포함되나 sensor·inspection·alarm 도메인 미구현으로 이번 라운드 범위 밖. 프론트는 optional 폴백이라 안전하며, 해당 도메인 구현 시 DTO 확장 + 프론트 표시 재검증 필요.
- **디자인 토큰 준수(docs/04 §1)** — 이번 검증 범위를 경계면·상태머신·컨벤션으로 한정. `equipment.css` / `layout.css` 의 하드코딩 색상 여부는 미검사(별도 UI QA 라운드 권장).
- **임계치 판정 / PM 일정 계산 / KPI 계산** — 3개 핵심 로직 모두 이번 라운드 미구현이라 단위 테스트 검증 대상 아님(상태 머신 1개만 존재·통과). CLAUDE.md "핵심 4대 로직 단위 테스트 필수"는 해당 기능 구현 라운드에서 재확인.
