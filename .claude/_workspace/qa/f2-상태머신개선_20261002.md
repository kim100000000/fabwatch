## 2. 권한 구멍 점검 (통과, LOW 2건)

(a) 다른 쓰기 엔드포인트 권한 약화: 없음. `git diff` 상 @PreAuthorize 제거는 `PATCH /equipments/{id}/status` 1곳뿐. POST/PUT /equipments=ADMIN, PUT thresholds=ADMIN, SimulatorController 클래스 레벨 ADMIN·ENGINEER 모두 불변. `@EnableMethodSecurity` 유지, `anyRequest().authenticated()`로 PATCH status는 인증 필수.

(b) 역할 클레임 정합: `JwtTokenProvider.createAccessToken`이 `role` 클레임에 접두사 없는 `"ADMIN"|"ENGINEER"|"TECHNICIAN"`을 넣고, `toPrincipal`이 그대로 복원(JwtTokenProvider.java:42,59). `currentRole()`은 이 값을 반환하고 서비스는 `"ADMIN".equals`/`"ENGINEER".equals`로 비교 -> 접두사(ROLE_)는 JwtAuthenticationFilter에서 authority에만 붙으므로 불일치 없음.
 - 인증정보 없음: `currentRole()`이 401 UNAUTHORIZED로 fail-closed (도달 전에 필터 체인이 이미 401).
 - 역할 null/미지(예: role 클레임 부재): `engineerOrAbove=false` -> DOWN→IDLE 외 전부 403 = fail-closed. 단 아래 LOW-1 참조.

(c) autoDown 경로: `autoDown`은 public이지만 호출처가 `EquipmentAutoDownListener` 1곳(EquipmentDownRequestedEvent 수신)뿐이고 컨트롤러·타 도메인에서 호출 불가. 따라서 일반 PATCH API가 autoDown을 우회로로 쓸 수 없음. autoDown은 `canTransitionTo(DOWN)`만 확인(RUN/IDLE→DOWN만 성공, DOWN/PM은 조용히 스킵) -> 신규 DOWN→* 전이와 무관, 의도대로.
 - 참고(결함 아님, 기존 설계): `POST /alarms/manual`은 docs/06상 "전체" 권한이라 TECHNICIAN이 CRITICAL 수동 알람 -> 이벤트 -> autoDown(RUN/IDLE→DOWN)을 일으킬 수 있다. PATCH로는 TECHNICIAN의 RUN→DOWN이 403이므로 "수동 고장 보고" 경로의 의도적 예외로 보이나, docs/03 F-2에 이 우회가 TECHNICIAN에게 허용됨을 명시하면 면접 질문에 안전(LOW-6).

 - LOW-1 `EquipmentService.java:178-186` — `allRolesAllowed`(DOWN→IDLE)가 역할 값을 전혀 보지 않아 알 수 없는 역할 문자열/null도 통과한다("전 역할"의 fail-open). 현재는 서명된 JWT + DB enum Role에서만 role이 나오므로 실제 악용 경로 없음. 수정 제안: `Set.of(ADMIN, ENGINEER, TECHNICIAN).contains(actorRole)`를 선결 조건으로 추가해 미지 역할은 어떤 전이도 403.
 - LOW-2 `EquipmentController.java:71-76` — 권한 판정이 컨트롤러 어노테이션에서 서비스 내부로 이동해 `@PreAuthorize` 스캔(권한 매트릭스 감사)에서 이 엔드포인트가 "인증만"으로 보인다. 현재 Javadoc으로 설명돼 있어 허용 가능. 서비스 메서드가 다른 호출처에서 role을 임의 문자열로 넘길 수 있다는 점은 위 LOW-1과 같은 맥락.

- 시각/에러코드 컨벤션: INVALID_STATUS_TRANSITION(400)/VALIDATION_ERROR(400)/FORBIDDEN(403) ErrorCode 정의와 일치(ErrorCode.java:14,17,28).

## 미검증 항목
- 브라우저 실동작(다이얼로그 후보 버튼, 사유 입력 차단, 'DOWN (BM)' 시각 확인): 리더가 별도 검증 — 코드 기준으로만 판정.
- 실MySQL 환경: 이번에 서버를 띄우지 않음. 테스트는 H2 기준. status_log 정렬(changed_at DESC) 동시각 동률 가능성은 Instant 마이크로초 정밀도라 H2에선 문제 없음, MySQL 컬럼 정밀도(DATETIME(6)) 실DB 확인은 미수행.
- `npm run build`/tsc 및 프론트 린트: 실행하지 않음(타입은 소스 대조로만 확인).
- docs/04 화면 와이어의 'DOWN' 표기와 상태 변경 버튼 권한 문구, docs/05는 변경 필요 여부만 확인(필요 없음 판단), 상세 문서 리뷰는 미수행.
- 점검(BM) 이력 연계 강제(F-3)는 문서상 이후 단계라 이번 범위 외.
