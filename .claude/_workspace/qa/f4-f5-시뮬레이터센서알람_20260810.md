### F-1 [중] 신규 에러코드 4종이 프론트에 전혀 매핑되지 않음 — 검증 항목 1

`INVALID_THRESHOLD_RANGE` / `ACK_REQUIRED_FIRST` / `INVALID_ALARM_STATUS` / `SCENARIO_ALREADY_ACTIVE`

다만 폴백되는 서버 문구가 그대로 사용자에게 노출되므로 코드별 판단이 갈린다:

- **`INVALID_THRESHOLD_RANGE` — 실제 노출 결함.**
  `ThresholdRangeValidator.java:35-36,42-43` 이 던지는 message 는
  `"임계치 순서 위반(crit_low ≤ warn_low): 85 > 90"` 형태로 **DB snake_case 컬럼명이 최종 사용자 화면에 그대로 노출**된다.

  → 수정 방법: `errorMessage.ts` 에 사용자 문구로 매핑해 서버 message 폴백을 차단.
- **`SCENARIO_ALREADY_ACTIVE`** — 서버 문구가 짧고 다음 행동을 안내하지 않는다(데모 제어 패널 `DemoControlPanel.tsx:47` 에서 노출).
  → 수정 방법: 해제 후 재주입 안내를 담은 문구로 매핑.
- **`ACK_REQUIRED_FIRST` / `INVALID_ALARM_STATUS`** — 서버 message 에 `"현재 상태: OPEN"` 같은 실제 상태가 실려 있어
  (`Alarm.java:103-104,113-114`, `AlarmService.java:103-104`) 서버 문구 폴백이 더 유용하다.
  이는 이 파일이 이미 `NOT_FOUND` / `VALIDATION_ERROR` / `INVALID_STATUS_TRANSITION` 에 적용 중인 명시적 컨벤션과 동일하고,
  `AlarmResolveDialog.tsx:39` 에도 같은 의도가 기록돼 있다.
  → 수정 방법: 매핑하지 않되, **"의도적 미매핑"임을 주석으로 명시**해 다음 QA 라운드에 다시 결함으로 잡히지 않게 한다.

### F-3 [하] 존재하지 않는 클래스를 보안 완화책으로 인용하는 주석 — 검증 항목 5/6
