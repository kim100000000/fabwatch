### 1-4. 저장 후 반영/알람 판정 정합 — 통과
- 서버: 판정은 매 틱 `SensorIngestionService.ingest`(@Transactional)가 `sensorQueryService.findAllSpecs()`로 DB에서 직접 읽음(SensorQueryServiceImpl.java:19-21, 캐시 없음) → 커밋 이후 다음 틱(≤2초)부터 새 임계치. `getLatest`(SensorDataQueryService.java:43-58)도 DB 최신값 + `ThresholdEvaluator`로 level 재판정. 판정 규칙은 `ThresholdEvaluator` 한 곳(null=미사용, 경계값은 정상).
- 이력 원자성: `updateThresholds`는 단일 @Transactional — Sensor 갱신과 SensorThresholdLog 저장이 같은 트랜잭션(SensorThresholdService.java:50-87). old*는 변경 전 엔티티 값, changedBy는 SecurityUtils, changedAt은 Instant.now()(UTC). 실호출 로그에서 old→new 체인 일관 확인(로그 id 3→4).
- 프론트: `applyThresholds`가 서버 응답 4값으로 해당 센서를 교체(null 포함, useLatestSensors.ts:121-143), merged는 `latest !== undefined ? latest : detail`로 null을 상세의 옛 값으로 되돌리지 않음(SensorTabPanel.tsx:141-146). 라이브/이력 차트 기준선이 merged 센서를 쓰므로 즉시 갱신. SSE 이벤트는 임계치를 건드리지 않음.

### 1-5. 4값 전부 null이 판정/차트/DRIFT에 주는 영향 — NPE 없음, 의미상 주의 (M-2)
- ThresholdEvaluator: 모든 비교가 null 가드 → NORMAL. SensorLiveChart yDomain: thresholds 비면 값만으로 범위 계산. PromptBuilder `num()` null→"-". ScenarioParams.resolveDriftTarget: critHigh→warnHigh→critLow→warnLow→base×1.2 순으로 null 가드, NPE 없음.
- ScenarioParams.java(`return base >= 0 ? base * 1.2 : base * 1.2;`)는 두 분기가 같고, base=0이면 목표값=0 → slope 0이라 DRIFT가 아무것도 안 함(LOW L-9).

### 1-6. 진행 중 시뮬레이터/알람 중복 억제 부작용 — 결함 아님, 문서화 필요 (L-6, L-7)
- DRIFT는 주입 시점에 slope/targetValue/maxElapsedSec를 굳혀 저장(ScenarioParams, docs/03 F-4.2에 기재). 따라서 임계치를 올리면 plateau가 새 crit에 못 닿아 CRITICAL이 안 나고, 내리면 즉시 초과로 알람 — 사용자는 이유를 알 수 없음. 편집 다이얼로그 경고 문구/docs에 "진행 중 DRIFT는 주입 당시 목표값을 유지" 추가 권장.
- 중복 억제는 (equipment, sensor, severity, status≠RESOLVED) 기준(AlarmService.java:229-236). 임계치를 완화해도 이미 열린 알람은 자동 해소되지 않고 threshold_value는 옛 값 스냅샷으로 남음(의도된 동작일 가능성 높음 — docs/03 F-4.3에 명시 권장). 새 임계치로 재발생하려면 기존 알람 RESOLVE 필요.

## 4. HTTP 오류 핸들러 (405/415/406/파라미터 누락)

### 통과 (실호출 확인 포함)
| 케이스 | 호출 | 결과 |
|---|---|---|
| 406 | `Accept: application/xml` / `text/html`, 인증 GET /users/lookup | 406 `Content-Type: application/json`, `{"code":"NOT_ACCEPTABLE","message":..,"timestamp":..}` — JSON 강제(GlobalExceptionHandler.java 406 핸들러가 contentType 명시) |
| 405 | GET /auth/login(인증), GET .../thresholds(PUT 전용 경로) | 405 `{"code":"METHOD_NOT_ALLOWED",...}` 공통 포맷 (DELETE/PUT 등 변경 메서드는 미호출, 코드·HttpErrorFormatIntegrationTest로 판정) |
| 415 | 통합테스트 `POST /auth/login text/plain` | 415 UNSUPPORTED_MEDIA_TYPE (실호출 미수행: POST) |
| 404 | GET /api/v1/nope, GET /users/1 | NOT_FOUND 공통 포맷 |
| 400 | `?status=FOO`, `/equipments/abc/sensors`, `?workerId=abc` | VALIDATION_ERROR 공통 포맷 |
| 401(미인증) | 토큰 없이 405 대상 경로/Accept xml | 보안 필터가 먼저 UNAUTHORIZED 공통 포맷(정상 순서) |
- 본문에 스택트레이스/예외 클래스명 없음(테스트 noInternalDetailsLeaked + 실응답 확인). 405/415/406 메시지는 고정 한국어 문구라 프론트 `toUserMessage` 폴백(서버 message 그대로)으로 내부정보 노출 없이 표시 가능. 프론트는 분기를 code로만 함(ERROR_MESSAGE 맵, message 파싱 없음). `INVALID_THRESHOLD_RANGE`는 서버 message에 snake_case(crit_low ≤ warn_low)가 섞여 있어 프론트가 매핑 처리(errorMessage.ts) — 정상.
- ErrorCode 3종 추가 값 상태코드(405/415/406) 정의 일치.

### 결함
- **L-14 [LOW] 405 응답에 `Allow` 헤더 없음** — GlobalExceptionHandler.java(handleMethodNotAllowed)가 `build(...)`만 반환(실호출 헤더에서 Allow 확인 불가). RFC 9110상 405는 Allow를 포함해야 함. 수정: `ResponseEntity.status(405).allow(e.getSupportedHttpMethods().toArray(HttpMethod[]::new))`.
- **L-15 [LOW] 필수 파라미터 누락 400 핸들러가 현재 도달 불가+무테스트** — 코드베이스에 `required=true`(기본) @RequestParam이 한 곳도 없음(grep 0건). HttpErrorFormatIntegrationTest에도 이 케이스 없음 → "필수 파라미터 누락 400" 서술은 미검증. 같은 계열의 `MissingRequestHeaderException`, `MissingServletRequestPartException`, Spring 6.1+ `HandlerMethodValidationException`, `ServletRequestBindingException`은 여전히 `Exception` 핸들러로 가 500이 됨. 수정: `ServletRequestBindingException`(부모)·`HandlerMethodValidationException`을 400으로 매핑 + 가짜 컨트롤러 또는 단위 테스트 1건.
- **L-16 [LOW, 기존] `ConstraintViolationException` 핸들러가 `e.getMessage()`를 그대로 노출**(GlobalExceptionHandler.java:46) — `methodName.argN` 형태의 내부 식별자가 섞일 수 있음. 컨트롤러에 @Validated 파라미터 제약이 생기면 노출됨(현재 없음). 수정: violation의 propertyPath 마지막 노드+메시지만 조합.

### @Valid가 @PreAuthorize보다 먼저 평가되는 문제(리더 이월 항목) — 평가 및 완화안
- 확인: 스프링 MVC는 핸들러 메서드 호출 전에 인자 바인딩(@Valid, JSON 파싱, enum/타입 변환)을 하고, @PreAuthorize는 컨트롤러 빈 프록시의 메서드 진입 시점에 평가되므로 권한 없는 사용자의 형식 오류 요청은 403이 아니라 400(또는 415/405)이 먼저 나온다. 보안 필터 체인(인증)은 그 앞이라 **미인증은 401이 정상 선행**한다.
- 보안 영향 평가: **LOW**. (1) 400 본문은 DTO 필드 제약 메시지뿐(예: `reason: 변경 사유는 필수입니다.`)이라 이미 docs/06에 공개된 스키마 수준이고, (2) 리소스 존재 여부·비즈니스 규칙(INVALID_THRESHOLD_RANGE, 404 등)은 서비스 안에서 판정되므로 권한 없는 사용자에게는 항상 403이 먼저(리소스 열거 불가), (3) 상태 변경은 일어나지 않음. 남는 문제는 "권한 시도가 403으로 기록되지 않는다"는 감사/모니터링 노이즈와 응답 일관성(최소권한 원칙의 '인가 선행' 위반)이다.
- 완화안(권장 순): ① 관리자 전용·변경성 엔드포인트(임계치 PUT, 설비 POST/PUT, 시뮬레이터, 사용자 관리)를 `SecurityConfig`에 URL 규칙으로 선(先) 차단 — 예 `.requestMatchers(HttpMethod.PUT, "/api/v1/equipments/*/sensors/*/thresholds").hasRole("ADMIN")` — 필터 체인은 MVC 바인딩보다 앞서므로 403이 먼저 나오고 RestAccessDeniedHandler가 공통 포맷을 보장. `@PreAuthorize`는 이중 방어로 유지. ② 회귀 방지 테스트: 리플렉션으로 `@PreAuthorize`가 붙은 모든 POST/PUT/PATCH 핸들러를 순회해 "최저 권한 역할 + 쓰레기 본문 → 403" 파라미터화 테스트. ③ 대안 없이 수용하려면 docs/11 §3에 "형식 오류는 인가 이전에 400"을 명시하고 현 상태 유지(테스트로 고정).

- 브라우저 실동작(모달 포커스 동작, 임계치 저장 후 차트 기준선 즉시 갱신, 폴백 폴링 경쟁, 설비 전환 시 헤더 잔존, 필터 UI) — 리더가 별도 확인.
- PUT/POST/DELETE 실호출(임계치 수정 400/403/500 경로, 415, 405의 변경 메서드, @Valid→@PreAuthorize 순서의 실응답) — 데이터 변경 가능성 때문에 코드·테스트로만 판정. M-1(a)(b)(c)의 DB 반올림/500은 코드 추론(H2/MySQL 실동작 미확인).
- gradle 테스트 — 지시에 따라 미실행(리더 확인 427건 통과).
- 실MySQL에서 동시 임계치 수정(락/경쟁) 동작.
- 다른 역할(ADMIN/TECHNICIAN)로의 실호출 — 로그인 최소화로 engineer 1계정만 사용.
