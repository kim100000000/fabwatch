**가장 위험한 3개**

1. **H-1 비인증 세션 강제 종료**: `POST /auth/refresh`에 `{"refreshToken":"1.아무문자열"}`만 보내면 사용자 1(=admin)의 refresh token이 DB에서 삭제된다. 사용자 id가 1,2,3 순차라 인증 없이 누구든 모든 계정을 반복적으로 로그아웃시킬 수 있다. 단위 테스트가 이 동작을 그대로 고정하고 있다.
2. **H-2 계정 생성·비밀번호 변경 수단이 없음 + 알려진 시드 비밀번호**: prod에서는 시드가 꺼져 사용자 0명 → 로그인 자체가 불가. 운영자가 가장 쉽게 택하는 길은 시드를 켜는 것이고, 그러면 `admin@fabwatch.dev / fabwatch123`(코드·테스트·README·로그인 화면에 공개)이 인터넷에 열린다.
3. **H-3 로컬 빌드 jar에 `application-local.yml`(개발용 JWT 키, DB 비밀번호, seed.enabled=true)이 그대로 포함 + 기본 프로파일이 local**: docs/13 §4가 "로컬에서 `gradlew build`한 jar"를 배포 산출물로 안내한다. `SPRING_PROFILES_ACTIVE=prod`를 하나라도 빠뜨리면 운영에서 시드 계정 + 알려진 키로 부팅한다.

그 다음으로 공개 데모에서 체감이 큰 것: M-1(ENGINEER가 시뮬레이터 파라미터 하나로 전체 센서 수집 중단), M-2(알려진 이메일 3개 → 5회 오입력으로 전 계정 15분 잠금), M-3(레이트 리밋·본문 크기·SSE 연결 수 제한 전무).

## 2. 의도된 보안 설계 (docs/11, docs/06 권한 열, docs/03 F-1·F-7, CLAUDE.md)

- JWT HS256 Access 30분 + 불투명 Refresh 14일(DB 저장, 회전, 재사용 감지 시 전체 세션 무효화), 5회 실패 15분 잠금(429), BCrypt 10, 비활성 403.
- 인증 없는 API는 login/refresh(+health) 뿐. 역할은 `@PreAuthorize`, 상태 전이 역할은 서비스 내부. CORS는 env 화이트리스트, CSRF 비활성(Bearer 헤더). SSE만 `?token=` 허용.
- Claude는 백엔드 경유만, 키는 env, 로그/응답/DB 노출 금지, 일 20건 쿼터, 프롬프트 인젝션 방어, 마크다운 raw HTML 금지.
- 에러 포맷 `{code,message,timestamp}`, 스택트레이스 비노출, soft delete, 가상 데이터만.

구현은 이 설계의 대부분을 지킨다(§5 "문제 없음 확인"). 아래 발견은 (a) 설계 자체의 구멍과 (b) 설계와 구현의 불일치다.

## 4. 항목별 발견

### HIGH

**H-1 [코드+테스트 고정] 비인증 세션 강제 종료 (refresh 재사용 감지 오용)**
- 위치: `backend/src/main/java/com/fabwatch/auth/service/AuthService.java:73-90`, `JwtTokenProvider.java:63-84`(토큰 형식 `{userId}.{random}`), 근거 테스트 `backend/src/test/java/com/fabwatch/auth/service/AuthServiceTest.java:163-171`
- 근거: refresh는 토큰 앞부분 `userId`로 사용자를 찾고, 저장값과 다르면 "재사용"으로 보고 `user.clearRefreshToken()`을 커밋(noRollbackFor)한다. 발급된 적 없는 `"{USER_ID}.old-token"`으로도 사용자의 refresh가 null이 된다는 것을 위 단위 테스트가 그대로 검증한다. 사용자 id는 1,2,3 순차. 라이브 호출은 다른 에이전트의 브라우저 세션을 파괴하므로 실행하지 않았고, 존재하지 않는 id/형식 오류 4종은 모두 401 INVALID_TOKEN으로 부작용 없음을 확인했다(`999999.abc`, `abc`, `-1.x`, `0.x`).
- 영향: 인증 없이 `POST /auth/refresh {"refreshToken":"1.x"}` 반복 → admin 포함 모든 사용자가 access 만료(≤30분) 때마다 강제 재로그인. 공개 데모 방해가 사실상 무비용.
- 수정: refresh 토큰에 userId를 넣지 말고(불투명 랜덤 256bit), 서버는 SHA-256 해시로 조회한다. 미지의 토큰은 부작용 없이 401. "재사용 감지"는 직전 회전된 토큰의 해시를 `previous_refresh_hash`로 보관해 그것이 제시될 때만 세션 전체를 폐기한다. 이 변경이 M-4(평문 저장)도 같이 해결한다.

**H-2 [코드] 사용자 생성·비밀번호 변경 경로 부재 → 알려진 시드 비밀번호로 공개 배포될 위험 (공개 시 CRITICAL)**
- 위치: `LocalDataSeeder.java:57-58`(`@Profile("local")` + `seed.enabled`), `:62`(`SEED_PASSWORD = "fabwatch123"`), `application-prod.yml:20-21`(seed 꺼짐), `PasswordPolicy.java`(시드에서만 사용), `LoginPage.tsx:34-39`(로그인 화면에 시드 이메일 3개 노출), `README.md:107`(비밀번호 위치 안내), 테스트 다수가 평문 비밀번호 보유(git에 커밋됨, `git log -S fabwatch123`로 확인)
- 근거: 컨트롤러에 사용자 생성·비활성·비밀번호 변경 API가 없다(`/admin/users` 미구현, §3 #29). prod는 시드가 꺼져 있고 시더는 local 프로파일 전용이라 prod DB의 users 테이블은 비어 로그인 불가. docs/13 §4·§10은 "prod 최초 1회 시드"·"시연용 시드가 화면에 표시됨"을 요구하므로 운영자는 시더를 prod에서도 켜도록 코드를 고치게 되고, 그 순간 공개 URL에 `admin@fabwatch.dev/fabwatch123`이 생긴다. git remote가 GitHub이므로 저장소가 공개되면 비밀번호도 공개다.
- 시나리오: 방문자 → ADMIN 로그인 → 임계치 변경, 설비 무한 생성(삭제 API 없음), 시뮬레이터 남용, AI 쿼터 소진(§6 참조).
- 수정(우선순위순):
  1. 부트스트랩 관리자: `BOOTSTRAP_ADMIN_EMAIL`/`BOOTSTRAP_ADMIN_PASSWORD_HASH`(bcrypt) env로만 users가 비었을 때 1회 생성. 시드 비밀번호를 코드에서 제거하고, 데모 시드는 기동 시 랜덤 비밀번호를 만들어 INFO 로그로 1회만 출력하거나 env(`DEMO_PASSWORD`)에서 받는다.
  2. `LoginPage` 시드 계정 안내는 `import.meta.env.DEV`일 때만 렌더. README의 "비밀번호는 시드 코드에 있다" 문구 삭제.
  3. 공개 데모가 목적이면 데모 전용 계정을 읽기 전용(GET 외 거부)으로 두고, 쓰기 권한 계정은 비공개(§6 참조).
  4. 최소한 비밀번호 변경 API(`PATCH /auth/password`, PasswordPolicy 적용)를 추가.

**H-3 [코드+산출물 확인] 로컬 빌드 jar에 개발용 설정·시드가 내장, 기본 프로파일이 local**

Railway Nixpacks처럼 Git 소스 빌드면 해당 파일이 없어 안전하지만(이 경우 `JWT_SECRET` 미설정으로 기동 실패=안전하게 실패), 로컬 jar/로컬 Docker 빌드 경로에서는 `SPRING_PROFILES_ACTIVE=prod`를 빠뜨리는 순간 local 프로파일이 활성화되어 시드 계정(H-2)과 파일에 박힌 개발 JWT 키로 기동한다. 파일 자체는 jar 안에 비밀번호(`fabwatch_local`)와 JWT 키 평문을 담아 jar 공유 시 노출된다.

### MED

**M-1 [코드] 시뮬레이터 파라미터 무검증 → ENGINEER 한 번의 호출로 전체 센서 수집 중단**
- 위치: `ScenarioParams.java:59-76`(spike multiplier, step offset/offsetRatio, drift slopePerSec/durationMin 범위 검사 없음, 문자열 "NaN"·"1e308"도 `Double.parseDouble` 통과), `SensorData.java:29`(`decimal(10,2)`), `SensorIngestionService.java:45,77`(한 틱의 모든 센서를 한 트랜잭션 `saveAll`)
- 근거: 값이 ±1e8을 넘거나 NaN/Infinity가 되면 BigDecimal 변환 또는 INSERT가 실패한다. 한 틱 트랜잭션이 통째로 롤백되어 SSE 발행도 건너뛰고(afterSave 미실행) 2초마다 스택트레이스가 로그에 쌓인다. 시나리오는 DB에 active로 남아 재기동해도 계속된다(해제는 `DELETE /simulator/scenarios/{id}`로 가능). 라이브 재현은 파괴적이라 하지 않았다.
- 수정: 유형별 범위 clamp(multiplier 0.1~10, offsetRatio ±1, durationMin 1~1440, 유한값만), 센서 단위 try/catch로 한 센서 실패가 다른 센서를 막지 않게 분리.

**M-2 [라이브+코드] 로그인 잠금: 계정 잠금 DoS + 동시 요청 우회 + 사용자 열거**
- 위치: `AuthService.java:41-67`, `User.java:84-94`, `BaseEntity.java`(`@Version`/락 없음 — `grep @Version`은 AiReport 쪽 주석 외 0건)
- (a) 잠금 DoS: 이메일이 공개(로그인 화면)이고 5회 실패면 15분 잠금이라 3개 계정을 15회 요청으로 잠글 수 있다. 15분마다 반복하면 데모 로그인이 영구 불가. 라이브 미실시(계정 잠금 부작용).
- (b) 우회 `[코드, 미재현]`: failedLoginCount는 락/버전 없는 read-modify-write라 N개 병렬 요청이 같은 값 0을 읽고 1로 쓰면 증가분이 유실된다. 병렬도만큼 시도 횟수가 늘어나 5회 제한이 약해진다.
- (c) 열거 `[라이브]`: 존재하지 않는 이메일 응답 5.4~7.9ms vs 로그인 성공(BCrypt) 약 143ms. 실패 시에도 존재하는 계정만 BCrypt를 타므로 시간차로 구분 가능(`AuthService.java:44-46` 조기 반환). 존재하는 계정만 5회 후 429 ACCOUNT_LOCKED가 되고, 비밀번호가 맞고 비활성이면 USER_DISABLED가 나와 비밀번호 적중도 노출(`:61`).
- (d) CPU: 존재하는 이메일로 BCrypt(약 140ms) 요청을 무제한 보낼 수 있음(잠금 전까지). IP 단위 제한 없음.
- 수정: 잠금 카운터를 원자적 UPDATE(`failed_login_count = failed_login_count + 1`) 또는 `@Version`/비관적 락으로. 존재하지 않는 이메일도 더미 해시와 `matches`를 수행해 시간 평준화. 잠금은 (이메일+IP) 키로 하거나 지수 백오프 지연으로 바꿔 계정 DoS를 줄임. 비활성 판정을 비밀번호 검사 앞으로(동일 메시지). 로그인/리프레시 IP 레이트 리밋(bucket4j 또는 프록시).

**M-3 [라이브+코드] 레이트 리밋·요청 크기·SSE 연결 수 제한 전무**
- 근거 `grep`: rate-limit/bucket4j/throttle/max-http 0건. 요청 본문: 비인증 `POST /auth/login`에 2MB JSON을 보내 `400 VALIDATION_ERROR`로 파싱 완료까지 처리됨(0.086s) `[라이브]` → 본문 크기 상한 없음(수십 MB는 `[추측]`). SSE: 동일 토큰으로 40개 동시 연결 전부 200 `[라이브]`, 사용자·전체 상한 코드 없음(`SensorStreamService.java:37,48`). `broadcast`/`heartbeat`가 구독자 전부에 대해 스케줄러 스레드에서 동기 `send`(`:92,109`)하므로 읽지 않는 클라이언트가 쌓이면 수집·집계가 지연될 수 있다 `[추측]`. 인증 사용자 쓰기 계열(점검 이력 content 65,535자 × 무제한 건수, 수동 알람, 체크리스트 등)에도 빈도 제한 없음. AI는 일 20건 쿼터가 유일한 방어.
- 수정: 프록시(nginx/Caddy/Cloudflare)에서 `client_max_body_size 256k`, 로그인·리프레시 레이트 리밋, SSE 사용자당 3개·전체 200개 상한(초과 시 429), SSE 전송을 별도 큐/스레드로 분리, Spring `server.tomcat.max-swallow-size`/`max-http-form-post-size` 및 JSON 본문 필터.

**M-4 [라이브+코드] Refresh 토큰 평문 저장·슬라이딩 14일·단일 세션 정책의 보안 의미**
- 위치: `User.java:57-61`, `AuthService.java:110-119`
- 근거 `[라이브]`: `select length(refresh_token), left(refresh_token,6) from users` → 길이 82의 원문 토큰(`1.20af...`)이 DB에 그대로 있다(비밀번호는 `$2a$10$` BCrypt). DB 읽기 권한(백업, SQL 인젝션 무관한 운영자 접근, H-3의 포트 노출 M-8) = 14일 세션 탈취.
- 회전마다 만료가 `now+14d`로 갱신되어 쓰는 한 영구 세션(절대 수명 없음).
- 사용자당 토큰 1개: 두 번째 기기·두 번째 로그인(공격자의 알려진 비밀번호 로그인 포함)이 첫 기기의 refresh를 덮어쓰고, 첫 기기가 이후 refresh하면 "재사용"으로 판정되어 양쪽 모두 로그아웃된다(자기 DoS). 같은 브라우저 탭 두 개가 동시에 refresh해도 같은 경로.
- 수정: SHA-256 해시 저장 + 별도 테이블(docs/11 §2가 원래 말한 `refresh_tokens`, 기기별 행) + 절대 수명(예: 30일)과 회전 유예(30초 grace)로 동시 refresh 허용.

## 5. 문제 없음 확인 (근거 포함)

**인증/세션**
- JWT 위조 방어 `[라이브]`: `alg:none` 토큰, 잘못된 키로 서명한 HS256, 서명 없는 토큰 → 전부 401. `Jwts.parser().verifyWith(SecretKey)`(`JwtTokenProvider.java:52`)가 HMAC 알고리즘으로 고정(alg 혼동 불가), 만료는 `ExpiredJwtException`으로 `TOKEN_EXPIRED` 분기.
- JWT 키: 코드·yml에 기본값 없음(`application.yml:46` `${JWT_SECRET}`) → 미설정이면 기동 실패(안전하게 실패), 256bit 미만은 `Keys.hmacShaKeyFor`가 거부. 개발 키는 gitignore 파일에만 있고 git 히스토리에 없음(`git log -S"fabwatch-local-dev-secret"` 0건), 테스트 키는 `src/test`에만 존재.
- 쿼리 토큰은 `/api/v1/stream/` 접두사에서만 허용 `[라이브]`: 비SSE 경로의 `?token=` 401, `..`/`%2e%2e`/`.;`/`//..` 경로 우회 4종 모두 401.

## 7. 미검증 항목

- H-1·M-1·M-2(a,b)·M-6의 **라이브 재현**: 다른 에이전트의 브라우저 세션/데이터를 변경하는 파괴적 호출이라 실행하지 않았다. 코드와(H-1은) 기존 단위 테스트로 근거를 제시했다.
- 상태 전이 역할 판정(TECHNICIAN은 DOWN→IDLE만): 실제 설비 상태가 바뀌는 호출이 필요해 라이브 미검증, 코드(`EquipmentService.validateManualChange`)로만 확인.
- 페이징 상한 100의 라이브 증명(데이터가 100건 미만), SSE 느린 소비자의 수집 스레드 블로킹, 대용량(수십 MB) 본문 처리: 추정.
- 의존성: Gradle `dependencies` 전체 트리·전이 의존성, logback/snakeyaml 등은 미조회. OSV는 Maven 좌표와 버전이 정확할 때만 응답하므로 누락 가능.
- Railway/Vercel 실제 로그 정책(쿼리스트링 로깅 여부), nginx/Caddy 설정: 배포 구성이 아직 저장소에 없어 평가 불가(Dockerfile·vercel.json 없음).
- 브라우저에서의 CSP 실호환성, 접근성 아닌 보안 UI 흐름의 실브라우저 점검(다른 에이전트가 UI 점검 중이라 미수행).
- 인가표 #9의 `PATCH /equipments/{id}/status`, #24 `POST /alarms/manual`의 정상 경로, ack/resolve의 실제 호출은 데이터 변경이라 호출하지 않음(존재하지 않는 id만 호출해 404 확인).
