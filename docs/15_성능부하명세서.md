## 2. 부하 프로파일 (기준 규모)

docs/02 NFR-2 기준. 시드는 설비 5대 × 센서 (총 18개, 압력 미부착 설비 존재).

| 지표 | 값 | 산출 |
|---|---|---|
| 센서 쓰기 | 약 9 rows/초 | 18센서 ÷ 2초 주기 |
| 일 원본 적재 | 약 78만 행 | 9 × 86,400 (문서 표기 43만은 4센서×5설비=20 기준 근사치, 실제 시드 18센서 기준 재계산) |
| 원본 테이블 상시 크기 | 7일치 ≈ 550만 행 | 보존 7일 |
| 1분 집계 쓰기 | 18 UPSERT/분 | 센서당 1버킷 |
| 1분 집계 누적 | 영구(행 작음) | 18 × 1,440/일 ≈ 2.6만/일 |
| SSE 이벤트 | 약 9 msg/초 × 구독자 | 브로드캐스트 |

> 원본 43만 vs 78만: docs/02는 "4센서×5설비" 근사, 실제 시드는 압력 미부착 반영 18센서. **둘 다 동일 자릿수**라 결론 불변 — 상세 재계산은 이 문서를 원천으로 삼는다.

## 4. 쿼리·다운샘플링 전략

- **조회 기간별 소스 자동 선택** (docs/06 §3):
  - ≤ 1시간 → `sensor_data`(원본), `granularity: RAW`
  - > 1시간 → `sensor_data_1m`(집계), `granularity: 1M`
- 실시간 차트는 SSE 푸시 + 클라이언트 슬라이딩 윈도우(최근 5분/최대 150포인트) → 서버 조회 부하 없음.
- 목록 API는 전부 페이징(size=20 기본). 무한 조회 금지.
- `latest`(카드용)는 센서별 최신 1건 — 인덱스 `(sensor_id, measured_at)` 역순 이용.

## 5. DB 인덱스 · 커넥션 (docs/05 정합)

| 테이블 | 인덱스 | 용도 |
|---|---|---|
| sensor_data | (sensor_id, measured_at) | 이력 조회·최신값 ★ |
| sensor_data | (measured_at) | **7일 삭제 배치·1분 집계 시간 범위 스캔 ★** — 없으면 `DELETE … WHERE measured_at < ?`가 풀스캔(EXPLAIN `type=ALL`, 약 79만 행 실측; 운영 규모 약 550만 행)이라 수집 INSERT를 락 대기시킨다 |
| inspection_check_results | (inspection_id) | 점검 상세의 결과 조회 |
| checklist_items | (equipment_id) | 설비별 PM 템플릿 조회 |
| simulation_scenarios | (sensor_id) | 센서별 활성 시나리오 조회 |
| sensor_data_1m | UNIQUE(sensor_id, bucket_at) | 집계 UPSERT·조회 |
| equipment_status_logs | (equipment_id, changed_at) | KPI 계산 스캔 |
| alarms | (equipment_id, status), (status, occurred_at) | 미해결 조회·중복억제 |
| inspections | (equipment_id, started_at), (type, shift) | 이력 검색 |

- 중복 억제 조회 `WHERE equipment_id=? AND sensor_id=? AND severity=? AND status != 'RESOLVED'`는 `(equipment_id, status)` 인덱스로 커버.
- **쓰기 최적화**: 2초 주기 배치 insert는 개별 트랜잭션 남발 금지 — 틱당 묶어서 저장.
- **커넥션 풀(HikariCP)**: 무료 티어 MySQL max_connections 고려해 pool size 보수적. 스케줄러·SSE·요청이 커넥션을 동시에 쓰므로 고갈 주의. 기본 `maximum-pool-size=10`(`DB_POOL_MAX`), `connection-timeout=10s`(`DB_CONNECTION_TIMEOUT_MS`)를 명시한다.

### 5.1 수집 틱 흐름과 트랜잭션 경계 (안정성 감사 H-3)

이전에는 한 틱 전체(저장 → SSE 전송 → 알람 판정 → 자동 DOWN)가 **하나의 트랜잭션**이었다. 느린 SSE 클라이언트가 `emitter.send`에서 막히면 수집 스레드가 DB 커넥션과 미커밋 트랜잭션을 쥔 채 지연되고(fixedRate catch-up으로 커넥션 소진 가능), 리스너 예외 한 건이 18개 센서 틱 전체를 롤백했으며, 롤백된 알람의 SSE가 이미 나가 유령 토스트가 남았다. 현재 구조:

```
SensorScheduler(2s) → SensorIngestionService.ingest(at)   ← 트랜잭션 아님
 ├─ SensorDataSource.read(at)        (짧은 읽기 트랜잭션; 시나리오 만료 판정으로 쓰기 가능)
 ├─ [TX 1] sensor_data.saveAll(18건) → 커밋            ← 원본은 항상 먼저 확정
 └─ 커밋 이후, 센서별 try/catch(실패는 센서 ID·예외 클래스만 WARN)
     ├─ SSE `sensor` → 구독자별 큐에 적재만 하고 즉시 반환 (전송은 전용 스레드풀)
     └─ 임계치 초과면 ThresholdExceededEvent 발행
          └─ AlarmService.onThresholdExceeded  [TX 2, REQUIRES_NEW, 이벤트마다]
               ├─ 중복 억제 판정(먼저) → 알람 저장 → CRITICAL이면 EquipmentDownRequestedEvent
               ├─ EquipmentAutoDownListener → autoDown (같은 TX 2, 설비 행 락) ← 알람+DOWN 원자적
               └─ 커밋 후(AFTER_COMMIT) SSE `alarm`·`status` 발행
```

- 알람 저장과 자동 DOWN을 한 트랜잭션에 둔 이유: 따로 커밋하면 "알람은 있는데 DOWN은 실패"한 뒤 중복 억제 때문에 DOWN이 영영 재시도되지 않는다. 한 센서의 TX 2가 실패해도 다른 센서·TX 1(원본)은 영향이 없고, 실패한 센서는 다음 틱에 같은 판정으로 재시도된다.
- 억제된 알람(2초마다 들어오는 대부분의 이벤트)은 설비 코드 조회·메시지 조립 전에 걸러낸다.
- 상태 전환(`changeStatus`/`autoDown`)은 설비 행을 `PESSIMISTIC_WRITE`로 잠그고 락 이후 최신 상태로 판정한다(M-1).
- **DATETIME(3)** 밀리초 정밀도 유지(측정 시각 정렬). H2 대체 테스트 시 방언 차이 주의(docs/12 §2).

## 6. SSE 성능 규칙

- 엔드포인트: `/stream/sensors?equipmentId=`(설비 구독) / 생략 시 전체 라인(메인 대시보드).
- heartbeat 30초로 유휴 연결 유지·죽은 연결 감지. heartbeat도 이벤트와 같은 구독자 큐를 거친다.
- **비동기 전송 (H-3)**: 이벤트는 수집 스레드에서 직접 `send`하지 않고 구독자별 유한 큐(`SSE_QUEUE_CAPACITY`, 기본 100)에 넣은 뒤 전용 스레드풀(`SSE_SENDER_THREADS`, 기본 8)이 구독자별로 직렬 전송한다. 큐가 가득 차거나 한 번의 전송이 `SSE_SEND_TIMEOUT_MS`(기본 5초)를 넘게 막혀 있으면 그 구독자만 `complete`로 끊고 구독 맵에서 제거한다(프론트는 재연결). 기존 전역/사용자별 연결 상한·정리 콜백과 독립적으로 동작한다. 한계: 막힌 소켓 쓰기는 인터럽트할 수 없어 Tomcat 쓰기 타임아웃까지 전송 스레드 1개를 점유한다(막힌 구독자가 스레드 수보다 많으면 다른 구독자 전송도 지연될 수 있음).
- `alarm`·`status` 이벤트는 `@TransactionalEventListener(AFTER_COMMIT)`로 받아 **커밋된 뒤에만** 내보낸다.
- 이벤트 종류 `sensor`/`alarm`/`status`만. payload 최소화(원본 배열 푸시 금지, 틱당 최신값만).
- 연결 인증은 쿼리 토큰 1회 검증(보안 명세 §4). 만료 30분으로 노출 창 제한.
- **폴백**: SSE 불가 시 3초 폴링(docs/07 버퍼) — 폴링은 `latest` API 사용, 부하 예측 가능.

## 7. 배치·보존 성능 (docs/05 §3)

| 배치 | 주기 | 성능 유의 |
|---|---|---|
| 1분 집계 UPSERT | 1분 | 직전 1분 원본만 스캔(measured_at 범위) — 전체 스캔 금지 |
| 원본 7일 삭제 | 일 1회 03:30 UTC (`zone="UTC"` 명시) | 대량 삭제는 **청크 삭제**로 락·복제지연 방지. 파티셔닝은 과설계 → 미채택 |
| PM OVERDUE 스캔 | 시간당/일1회 | pm_schedules 소량 — 부담 없음 |

### 7.1 원본 7일 삭제 배치 (청크 삭제 구현, H-2)

- `DELETE FROM sensor_data WHERE measured_at < :cutoff LIMIT :chunkSize`(MySQL·H2 모두 지원)를 **청크마다 별도 트랜잭션**으로 반복한다. 청크 크기 `SENSOR_PURGE_CHUNK_SIZE`(기본 10,000, 상한 100,000), 청크 사이 `SENSOR_PURGE_CHUNK_PAUSE_MS`(기본 100ms)만큼 쉬어 수집 INSERT에 락·IO 여유를 준다.
- 종료 조건: 한 청크의 삭제 건수가 chunkSize 미만이면 종료(정확히 배수면 빈 청크 1회 후 종료). 인터럽트(종료 신호) 시 즉시 중단. 중간 실패 시 이미 지운 청크는 유지되고 다음 날 이어서 지운다.
- 결과는 INFO 1줄로 남긴다: `센서 원본 보존 배치: <cutoff> 이전 N건 삭제 (청크 K회, chunkSize=…, …ms)`.
- 인덱스 `sensor_data(measured_at)` 필수. MySQL 8.0 EXPLAIN 실측(40만 행 스크래치 테이블): 인덱스 전 `type=ALL, rows≈398,784` → 인덱스 후 `type=range, key=idx_sensor_data_measured, rows≈5,782`(cutoff 근처)~199,392(범위가 넓을 때; LIMIT로 실제 스캔은 청크만큼), 10,000행 삭제 약 50ms.
- 규모 추정: 하루 약 78만 행 → 청크 78회 × (삭제 수십 ms + 대기 100ms) ≈ 15초 이내.

## 8. 부하 테스트 (경량 — Should)

- 목적: SLO(§1) 위반 지점 확인. 대규모 벤치마크 아님.
- 도구: k6 또는 JMeter 소규모 스크립트.
- 시나리오:
  1. LOAD-1: 이력 조회(24h) 동시 20 → PF-3 확인.
  2. LOAD-2: SSE 20 연결 유지 + 시뮬레이터 가동 → PF-1/PF-5 확인.
  3. LOAD-3: KPI 조회 반복 → PF-4 및 인덱스 효과 확인.
- 일정 부족 시: LOAD-2만 수동 확인(브라우저 탭 다중) + 결과 memory.md 기록.
