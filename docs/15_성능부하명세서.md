> 목적: 시뮬레이터가 쉼 없이 데이터를 쏟아내는 시스템에서 **어디가 먼저 아픈지**를 미리 정의하고, 무료 티어 안에서 시연이 끊기지 않게 한다. 대규모 최적화가 아니라 "병목 예측 + 근거 있는 수치"가 포트폴리오 포인트.

## 2. 부하 프로파일 (기준 규모)

docs/02 NFR-2 기준. 시드는 설비 5대 × 센서 (총 18개, 압력 미부착 설비 존재).

| 지표 | 값 | 산출 |
|---|---|---|
| 센서 쓰기 | 약 9 rows/초 | 18센서 ÷ 2초 주기 |
| 일 원본 적재 | 약 78만 행 | 9 × 86,400 (문서 표기 43만은 4센서×5설비=20 기준 근사치, 실제 시드 18센서 기준 재계산) |
| 원본 테이블 상시 크기 | 7일치 ≈ 550만 행 | 보존 7일 |
| 1분 집계 쓰기 | 18 UPSERT/분 | 센서당 1버킷 |
| 1분 집계 누적 | 영구(행 작음) | 18 × 1,440/일 ≈ 2.6만/일 |
| SSE 이벤트 | 약 9 msg/초 × 구독자 | 브로드캐스트 |

> 원본 43만 vs 78만: docs/02는 "4센서×5설비" 근사, 실제 시드는 압력 미부착 반영 18센서. **둘 다 동일 자릿수**라 결론 불변 — 상세 재계산은 이 문서를 원천으로 삼는다.

## 3. 병목 지점 & 대응 (예측 우선순위)

| 순위 | 병목 | 증상 | 대응 |
|---|---|---|---|
| 1 | 원본 테이블 무한 증가 | 조회 느려짐, 디스크 압박 | 7일 삭제 배치(§7) + 조회는 집계 우선(§4) |
| 2 | 이력 차트 원본 풀스캔 | 24h 조회 시 수십만 행 | 1시간 초과는 `sensor_data_1m` 자동 선택 (docs/06 §3) |
| 3 | SSE 브로드캐스트 팬아웃 | 구독자↑ 시 지연 | 설비별 구독 분리 + heartbeat 30초 + 폴링 폴백 |
| 4 | 임계치 판정 중복 알람 | 알람 폭주 → DB 쓰기 폭증 | 중복 억제(docs/03 F-4.3)로 근본 차단 |
| 5 | KPI 매 요청 재계산 | status_log 스캔 반복 | 인덱스(§5) + 필요 시 결과 캐시(Should) |
| 6 | 무료 티어 콜드스타트 | 첫 응답 수 초 | 시연 전 워밍업(docs/13 §7) |

## 4. 쿼리·다운샘플링 전략

- **조회 기간별 소스 자동 선택** (docs/06 §3):
  - ≤ 1시간 → `sensor_data`(원본), `granularity: RAW`
  - > 1시간 → `sensor_data_1m`(집계), `granularity: 1M`
- 실시간 차트는 SSE 푸시 + 클라이언트 슬라이딩 윈도우(최근 5분/최대 150포인트) → 서버 조회 부하 없음.
- 목록 API는 전부 페이징(size=20 기본). 무한 조회 금지.
- `latest`(카드용)는 센서별 최신 1건 — 인덱스 `(sensor_id, measured_at)` 역순 이용.

## 5. DB 인덱스 · 커넥션 (docs/05 정합)

| 테이블 | 인덱스 | 용도 |
|---|---|---|
| sensor_data | (sensor_id, measured_at) | 이력 조회·최신값 ★ |
| sensor_data_1m | UNIQUE(sensor_id, bucket_at) | 집계 UPSERT·조회 |
| equipment_status_logs | (equipment_id, changed_at) | KPI 계산 스캔 |
| alarms | (equipment_id, status), (status, occurred_at) | 미해결 조회·중복억제 |
| inspections | (equipment_id, started_at), (type, shift) | 이력 검색 |

- 중복 억제 조회 `WHERE equipment_id=? AND sensor_id=? AND severity=? AND status != 'RESOLVED'`는 `(equipment_id, status)` 인덱스로 커버.
- **쓰기 최적화**: 2초 주기 배치 insert는 개별 트랜잭션 남발 금지 — 틱당 묶어서 저장.
- **커넥션 풀(HikariCP)**: 무료 티어 MySQL max_connections 고려해 pool size 보수적(예: 5~10). 스케줄러·SSE·요청이 커넥션을 동시에 쓰므로 고갈 주의.
- **DATETIME(3)** 밀리초 정밀도 유지(측정 시각 정렬). H2 대체 테스트 시 방언 차이 주의(docs/12 §2).

## 6. SSE 성능 규칙

- 엔드포인트: `/stream/sensors?equipmentId=`(설비 구독) / 생략 시 전체 라인(메인 대시보드).
- heartbeat 30초로 유휴 연결 유지·죽은 연결 감지.
- 이벤트 종류 `sensor`/`alarm`/`status`만. payload 최소화(원본 배열 푸시 금지, 틱당 최신값만).
- 연결 인증은 쿼리 토큰 1회 검증(보안 명세 §4). 만료 30분으로 노출 창 제한.
- **폴백**: SSE 불가 시 3초 폴링(docs/07 버퍼) — 폴링은 `latest` API 사용, 부하 예측 가능.

## 7. 배치·보존 성능 (docs/05 §3)

| 배치 | 주기 | 성능 유의 |
|---|---|---|
| 1분 집계 UPSERT | 1분 | 직전 1분 원본만 스캔(measured_at 범위) — 전체 스캔 금지 |
| 원본 7일 삭제 | 일 1회(새벽) | 대량 삭제는 **청크 삭제**(LIMIT 반복)로 락·복제지연 방지. 파티셔닝은 과설계 → 미채택 |
| PM OVERDUE 스캔 | 시간당/일1회 | pm_schedules 소량 — 부담 없음 |

## 8. 부하 테스트 (경량 — Should)

- 목적: SLO(§1) 위반 지점 확인. 대규모 벤치마크 아님.
- 도구: k6 또는 JMeter 소규모 스크립트.
- 시나리오:
  1. LOAD-1: 이력 조회(24h) 동시 20 → PF-3 확인.
  2. LOAD-2: SSE 20 연결 유지 + 시뮬레이터 가동 → PF-1/PF-5 확인.
  3. LOAD-3: KPI 조회 반복 → PF-4 및 인덱스 효과 확인.
- 일정 부족 시: LOAD-2만 수동 확인(브라우저 탭 다중) + 결과 memory.md 기록.

## 9. 측정 & 근거 남기기 (포트폴리오)

- 대표 쿼리 `EXPLAIN`으로 인덱스 사용 확인 → README 트러블슈팅 항목화.
- "원본 풀스캔 → 집계 전환으로 24h 조회 Xms→Yms" 같은 **개선 전후 수치**를 1건 이상 확보(면접 어필).
- 측정값·병목 발견은 memory.md 로그 + 필요 시 docs/10 ADR로.
