## 1. 테스트 전략 (원칙)

| # | 원칙 | 이유 |
|---|---|---|
| T-1 | 핵심 도메인 로직은 **단위 테스트 필수** | 임계치·PM·KPI·상태머신은 틀려도 화면상 그럴듯해 보인다 → 자동 검증만이 안전망 |
| T-2 | 나머지는 **얇게** — 대표 통합 테스트 + 수동 시나리오로 대체 | 1개월 일정에서 CRUD 전수 테스트는 낭비 |
| T-3 | 외부 의존(Claude API)은 **반드시 목(mock)** | 비용·비결정성·쿼터 때문에 실호출 금지 |
| T-4 | 테스트도 시각은 UTC 기준, 교대 판정은 KST 경계값 반드시 포함 | 시각 버그가 이력·KPI를 조용히 오염시킴 |
| T-5 | 일정 압박 시 버림 우선순위: E2E → 통합 → 단위. **단위는 마지막까지 사수** | docs/07 버퍼 규칙("테스트는 임계치+PM 계산 2개만")과 정합 |

## 2. 테스트 피라미드 & 도구

```
        ▲  E2E (수동 시나리오 중심, 자동화는 여유 시)
       ───  통합 테스트 (@SpringBootTest, 대표 플로우만)
      ─────  단위 테스트 (도메인 서비스·유틸 — 두껍게) ★
```

| 계층 | 백엔드 | 프론트 |
|---|---|---|
| 단위 | JUnit 5 + AssertJ + Mockito | Vitest (+ Testing Library, 여유 시) |
| 통합 | @SpringBootTest + Testcontainers(MySQL) 또는 H2 | — |
| E2E | 수동 시나리오(§7). 자동화는 Should | (동일) |
| 커버리지 | JaCoCo (도메인 패키지 한정 리포트) | — |

- **DB 통합 테스트는 Testcontainers(MySQL 8) 권장.** H2로 대체 시 방언 차이(UPSERT, DATETIME(3), ENUM) 주의 → 대체했다면 그 사실을 memory.md에 기록.
- 테스트 프로파일 `application-test.yml`: 스케줄러(@Scheduled) 비활성화, 시뮬레이터 off, Claude 클라이언트는 목 빈으로 교체.

## 3. 커버리지 목표 (현실적)

| 대상 | 목표 | 비고 |
|---|---|---|
| `common.util`(교대 판정 등), 도메인 계산 로직 | 라인 80%+ | 사수 대상 |
| equipment 상태머신, sensor 임계치 판정, inspection PM 계산, KPI 계산 | 분기 커버(주요 경계값) | ★ 필수 4종 |
| controller/repository | 대표 케이스만 | 전수 X |
| 전체 | 수치 목표 없음 | 커버리지%를 목표로 삼지 않는다 (T-1) |

## 4. 핵심 도메인 단위 테스트 케이스 ★

CLAUDE.md·docs/07이 지정한 4대 필수 로직. 각 케이스는 정상 + 경계 + 예외를 반드시 포함한다.

### 4.1 임계치 판정 (sensor) — docs/03 F-4.3
| # | 입력 | 기대 |
|---|---|---|
| TH-1 | warn_low < value < warn_high | NORMAL, 알람 없음 |
| TH-2 | value = warn_high (경계) | 판정 규칙대로(초과 기준인지 이상 기준인지 명시) — WARNING |
| TH-3 | value > crit_high | CRITICAL |
| TH-4 | 임계치 컬럼 NULL(미사용 센서) | 판정 스킵, 알람 없음 |
| TH-5 | 동일 설비+센서+심각도 미해결 알람 존재 | **중복 억제** — 신규 알람 생성 안 함 |
| TH-6 | CRITICAL 최초 발생 | 알람 생성 + 설비 상태 DOWN 전환 이벤트 발행 |
| TH-7 | crit_low > value (하한 위반) | CRITICAL |

### 4.2 상태 머신 (equipment) — docs/03 F-2
| # | 전환 | 기대 |
|---|---|---|
| SM-1 | RUN → IDLE, IDLE → RUN | 허용 |
| SM-2 | RUN → DOWN, IDLE → DOWN | 허용(자동/수동) |
| SM-3 | DOWN → PM | 허용 |
| SM-4 | PM → IDLE | 허용 |
| SM-5 | **PM → RUN** | 거부 → `INVALID_STATUS_TRANSITION` (현장 원칙: 시운전 경유) |
| SM-6 | DOWN → RUN | 거부 |
| SM-7 | 임의 허용외 전환 전수 | 거부 |
| SM-8 | 모든 성공 전환 | `equipment_status_logs`에 1건 기록 (KPI 원천) |

### 4.3 PM 스케줄 계산 (inspection) — docs/03 F-3.3
| # | 입력 | 기대 |
|---|---|---|
| PM-1 | DAILY, last_done=오늘 08:00 | next_due = +1일 |
| PM-2 | WEEKLY(cycle_value=요일) | 다음 해당 요일로 계산 |
| PM-3 | MONTHLY(일자=28) | 다음 달 28일 |
| PM-4 | next_due 경과 | 상태 OVERDUE 판정 |
| PM-5 | OVERDUE 3일 초과 & 미발송 | MAJOR "PM 지연" 알람 생성, `overdue_alarm_sent=true` |
| PM-6 | 이미 발송된 OVERDUE | 알람 재생성 안 함(중복 방지) |
| PM-7 | PM 이력 등록 | last_done 갱신 → next_due 재계산, overdue 플래그 리셋 |

### 4.4 KPI 계산 (equipment) — docs/03 F-5.4
| # | 입력(status_log) | 기대 |
|---|---|---|
| KPI-1 | DOWN 0회 | MTBF "고장 없음"(0 나눗셈 방지) |
| KPI-2 | RUN 구간 합 / DOWN 횟수 | MTBF 정확 계산 |
| KPI-3 | DOWN~PM종료 합 / DOWN 횟수 | MTTR 정확 계산 |
| KPI-4 | 가동률 = RUN / (전체 − PM) | 분모에서 PM 제외 확인 |
| KPI-5 | 기간 경계(오늘/주/월) 걸친 구간 | 기간 내로 절삭 계산 |
| KPI-6 | 열린 구간(현재 진행 상태) | 조회 시각까지로 계산 |

### 4.5 교대 판정 유틸 (common.util) — docs/03 F-7
| # | 입력(UTC) → KST | 기대 |
|---|---|---|
| SH-1 | KST 08:00 | D (경계 시작) |
| SH-2 | KST 19:59 | D |
| SH-3 | KST 20:00 | N (경계) |
| SH-4 | KST 07:59 | N (전일 야간 소속 여부 규칙 명시) |
| SH-5 | UTC→KST 날짜 넘어가는 값 | 소속 교대·날짜 정확 |

## 5. 통합 테스트 (대표 플로우만)

| # | 시나리오 | 검증 |
|---|---|---|
| IT-1 | 로그인 → 토큰 → 보호 API 호출 | 인증/인가 동작, 403/401 코드 |
| IT-2 | 로그인 5회 실패 | 429 `ACCOUNT_LOCKED`, 15분 잠금 |

| IT-4 | BM 이력 등록(alarmId 포함) | 알람 자동 RESOLVED, cause4m 누락 시 400 `CAUSE_4M_REQUIRED` |
| IT-5 | 알람 resolve (ACK 없이) | 400 `ACK_REQUIRED_FIRST` |
| IT-6 | 센서 조회 granularity 자동 선택 | 1시간 이내 RAW / 초과 1M |
| IT-7 | 권한 매트릭스 스팟체크 | TECHNICIAN이 설비 등록 시 403 |

## 6. AI 리포트 테스트 (Claude 목 처리) — T-3

- `ClaudeClient`를 인터페이스로 두고 테스트에선 **Fake 구현** 주입 (실호출 금지).
- AI-1: 정상 응답 → status DRAFT, draft_content 저장.
- AI-2: 타임아웃/5xx → 1회 재시도 후 status FAILED + fail_reason.
- AI-3: 일일 쿼터 초과 → 403 `AI_QUOTA_EXCEEDED` (호출 자체가 발생하지 않아야 함).
- AI-4: 확정 시 draft_content 불변, final_content만 갱신 (원본 보존 검증 — 면접 포인트).
- AI-5: 프롬프트에 개인정보(이메일/비밀번호) 미포함 확인(보안 명세 §7).

## 7. E2E 수동 시나리오 (릴리스 전 필수 체크)

docs/07 주차별 "완료 기준"과 동일한 시연 흐름. 릴리스/배포 전 이 3개는 손으로 반드시 통과.

1. **실시간 흐름**: 드리프트 주입 → 차트 상승 → WARNING → CRITICAL → 설비 자동 DOWN → 토스트 표시.
2. **점검 흐름**: DOWN 설비 BM 등록(4M) → 연계 알람 RESOLVED → 상태 전환 확인 → 이력 검색 노출.
3. **AI 흐름**: 알람에서 리포트 생성(GENERATING→DRAFT) → 편집 → 확정(CONFIRMED) → 목록 노출.
