## ADR-1. MSA를 하지 않고 모듈러 모놀리스를 선택 ★핵심

### 상황
MES 설비관리 시스템. 1인 개발, 1개월, 무료/저비용 배포(Railway+Vercel). 포트폴리오이자 향후 SaaS 후보.

### 선택지
1. MSA (서비스별 분리 배포) — 트렌드 어필 가능하지만 경험 없음
2. 단순 모놀리스 (레이어드 아키텍처) — 빠르지만 확장 근거 없음
3. **모듈러 모놀리스 (도메인 경계 강제 + 단일 배포)** ← 채택

### 결정 이유
- **규모의 논리**: MSA의 이득(팀별 독립 배포, 장애 격리, 개별 스케일링)은 전부 "여러 팀/대규모 트래픽" 전제. 1인 개발에선 이득이 0이고 비용(서비스 간 통신, 분산 트랜잭션, 배포비 N배, 로컬 실행 복잡도)만 남는다.
- **업계 흐름**: MSA 과잉 도입에 대한 반성이 최근 트렌드. "처음부터 MSA"가 아니라 "모놀리스로 시작해 경계가 검증되면 분리"가 현재 정석 (Spring Modulith가 이 흐름의 산물).
- **수익화 관점**: SaaS 초기(고객 0~100)는 모놀리스가 운영비·배포 단순성에서 압도적. 쪼갤 시점은 트래픽이 증명한 뒤.

### 대신 한 것 (그냥 모놀리스가 아니라는 근거)
1. 도메인 우선 패키지 분리: `com.fabwatch.{auth, equipment, sensor, inspection, alarm, aireport, simulator, common}` — 각 패키지가 곧 서비스 후보 경계
2. **도메인 간 직접 참조 금지**: 다른 도메인의 repository/entity를 직접 부르지 않고, service 인터페이스 또는 스프링 이벤트로만 통신 (예: 임계치 초과 → `ThresholdExceededEvent` 발행 → alarm 모듈 수신)
3. 분리 1순위 후보를 미리 지정: **simulator**(실설비 연동 시 게이트웨이 서비스로 독립), **aireport**(AI 호출량 증가 시 비동기 워커로 독립)
4. (여유 시) Spring Modulith로 모듈 경계 위반 검증 테스트 추가

### 면접 답변 (그대로 말하기)
> "MSA를 검토했지만 채택하지 않았습니다. MSA의 이점은 팀 단위 독립 배포와 장애 격리인데, 1인 개발 규모에서는 그 이점이 없고 분산 시스템의 비용만 떠안게 된다고 판단했습니다. 대신 모듈러 모놀리스로 도메인 경계를 패키지 수준에서 강제하고, 도메인 간 통신을 이벤트 기반으로 분리했습니다. 그래서 트래픽이 늘면 시뮬레이터와 AI 리포트 모듈부터 서비스로 떼어낼 수 있는 구조입니다. '아키텍처는 규모가 증명한 뒤에 진화시킨다'는 원칙으로 설계했습니다."

**꼬리 질문 대비**
- Q. "그럼 MSA로 전환한다면 뭐부터 하실 건가요?"
  → "simulator부터입니다. 이미 인터페이스로 추상화돼 있고 상태를 공유하지 않아서, REST/메시지 큐로 떼어내는 비용이 가장 낮습니다. 다음은 aireport인데, 외부 API 의존이라 지연이 크고 큐 기반 비동기 처리가 자연스럽기 때문입니다."
- Q. "이벤트 기반 통신에서 트랜잭션은요?"
  → "모놀리스 내부라 `@TransactionalEventListener`로 커밋 후 처리합니다. 서비스 분리 시점에는 아웃박스 패턴이 필요하다는 것까지 인지하고 있습니다."

## ADR-2. 백엔드: 레이어 우선이 아닌 도메인 우선 패키지

- 선택지: `controller/ service/ repository/` 최상위(레이어드) vs 도메인별 수직 분할
- 결정: 도메인 우선. 레이어 우선은 기능 하나 수정에 패키지 3~4곳을 오가고, 도메인 경계가 코드에 드러나지 않음.
- 면접 한 줄: "패키지 구조가 곧 아키텍처 문서가 되도록, 화면·기능 단위가 아니라 비즈니스 도메인 단위로 잘랐습니다."

## ADR-3. 프론트: FSD 라이트 (app / pages / features / shared)

- 결정: 컴포넌트 종류별(components/, hooks/) 분류 대신 기능별 분류. 풀 FSD의 entities/widgets 계층은 과해서 생략.
- 근거: 백엔드 도메인과 프론트 features가 1:1 대응 → 기능 추가 시 양쪽에서 같은 이름의 폴더만 만지면 됨.
- 면접 한 줄: "프론트 features와 백엔드 도메인 패키지를 1:1로 맞춰서, 기능 단위 작업 범위가 양쪽에서 동일하게 잡히도록 했습니다."

## ADR-4. 실시간: WebSocket이 아닌 SSE

- 근거: 센서/알람은 서버→클라이언트 단방향. 양방향이 필요 없는데 WebSocket을 쓰면 연결 관리 비용만 증가. SSE는 HTTP 기반이라 인프라(프록시, 인증 헤더) 호환이 쉽고 자동 재연결 내장.
- 폴백: SSE가 배포 환경에서 막히면 3초 폴링 (docs/07 버퍼 규칙).
- 면접 한 줄: "요구사항이 단방향 푸시였기 때문에 SSE를 선택했습니다. 기술은 필요가 결정한다는 기준입니다."

## ADR-5. 이상탐지: ML이 아닌 임계치 판정 + AI 요약

- 근거: 현장에서 실제 1차 감지는 임계치·인터락. ML 이상탐지는 데이터 축적과 검증 없이는 오탐 폭주 → 현장이 알람을 무시하게 됨 (실제 현장에서 본 실패 패턴). MVP는 검증된 규칙 기반 + AI는 "판단"이 아닌 "보고서 작성 노동 절감"에 투입.
- 확장: 이동평균/표준편차 밴드 → ML은 2단계 로드맵에 명시.
- 면접 한 줄: "AI를 탐지에 쓰지 않고 문서화에 쓴 이유는, 현장에서 오탐 알람이 신뢰를 잃는 과정을 직접 봤기 때문입니다."

## ADR-6. AI 리포트: 초안(draft)과 확정본(final) 분리 보존

- 근거: AI 출력을 무검증으로 공식 기록화하면 안 됨(환각 리스크). 엔지니어 검토·수정 후 확정하는 휴먼 인 더 루프 설계. 원본 보존으로 AI 출력 품질 추적도 가능.
- 면접 한 줄: "AI는 초안 작성자, 최종 책임은 엔지니어라는 현장 결재 구조를 데이터 모델에 그대로 반영했습니다."

## ADR-7. 센서 데이터: 원본 7일 + 1분 집계 영구

- 근거: 2초 주기 원본은 일 43만 건 — 무료 티어 DB에서 무한 보관 불가. 조회 패턴상 24시간 이후는 추세만 보므로 1분 min/max/avg 집계로 충분. 시계열 DB(InfluxDB) 도입은 MVP 규모에서 과잉.
- 면접 한 줄: "데이터 수명주기를 조회 패턴에 맞춰 설계해서, RDB만으로 비용과 성능을 잡았습니다. 규모가 커지면 시계열 DB로 교체할 지점도 sensor 모듈 안에 격리돼 있습니다."

## ADR-8. 시뮬레이터를 별도 모듈 + 인터페이스로 추상화

- 근거: 실설비가 없어서 시뮬레이터를 쓰지만, `SensorDataSource` 인터페이스 뒤에 두면 실제 PLC 어댑터(OPC-UA/Modbus)로 교체 가능. "가짜 데이터"가 아니라 "교체 가능한 데이터 소스 구현체 중 하나".
- 이상 패턴 3종(DRIFT/SPIKE/STEP)은 현장에서 관찰한 실제 고장 전조 유형을 모델링 — 이 부분이 도메인 경험의 증거.

## ADR-9. 역할명 TECHNICIAN 유지 (MAINTENANCE 미채택)

- 근거: 역할은 사람(테크니션), Maintenance는 업무/부서 용어. 해외 CMMS 표준도 Technician. 화면 메뉴·이력서에서는 "Maintenance(설비보전)"를 업무 용어로 병용해 채용 키워드 양쪽 대응.

## ADR-10. 멀티테넌시: 설계만 하고 구현하지 않음

- 근거: 취업이 1순위 목표. 멀티테넌시는 지금 필요 없는 기능이지만, 나중에 추가 비용이 큰 항목이라 **전환 지점만 `// TENANT:` 주석으로 표시** (row-level tenant_id 방식 확정, docs/08 A-3).
- 면접 한 줄: "지금 필요 없는 건 만들지 않되, 나중에 비싸지는 결정만 미리 해뒀습니다. YAGNI와 확장성의 균형점이라고 생각합니다."

## ADR-11. 설비 상태 4개 유지, PD(파티클 등 오염 정지)는 상태로 넣지 않음

- 근거: 현장에서는 DOWN을 BM(하드웨어 고장)과 PD(대기 중 파티클 감지 등 오염으로 인한 정지)로 나눠 쓰지만, 둘 다 "계획 없는 정지"라 상태 머신 관점에서는 같은 DOWN이다. 상태를 5개로 늘리면 전이표(4x4→5x5), KPI 공식(가동률·MTBF·MTTR), DB, 문서, 테스트 수십 개가 바뀌는 데 비해 얻는 것은 색 하나다.
- 확장 지점: 필요해지면 상태가 아니라 **DOWN의 유형(`down_type` BM/PD)** 컬럼으로 추가한다. 수동 전환 다이얼로그에서 유형 선택, 자동 DOWN은 센서 종류로 분류, 배치도 색만 분기하면 되고 상태 머신은 그대로다. MTBF에 PD를 포함할지는 그때 정의한다.
- 면접 한 줄: "현장의 BM/PD 구분을 알고 있지만, 상태 머신은 4개로 단순화하고 구분은 DOWN의 유형으로 확장할 수 있게 남겨뒀습니다."
