# 01. 서비스 기획서 — FabWatch

> 버전 v1.0 / 2026-07-06 / 작성자: 김성태

## 1. 한 줄 정의

**"설비 점검 이력과 센서 데이터를 한 화면에서 관리하고, 고장이 나면 AI가 리포트 초안을 써주는 경량 설비관리 시스템(MES 설비 모듈)"**

## 2. 왜 이걸 만드는가

### 2.1 목적 (우선순위 순)
1. **취업**: 제조IT·스마트팩토리·MES 개발 직무 포트폴리오. 신입/주니어 지원자 중 "현장을 아는 개발자"라는 유일한 포지션 확보.
2. **수익화(후순위)**: 중소공장용 경량 설비관리 SaaS로 확장 가능한 구조를 처음부터 설계에 반영 (→ 08 문서).

### 2.2 차별점 — 왜 아무도 못 따라 하는가

일반 개발자 포트폴리오는 설비관리를 만들어도 "설비 CRUD + 차트"에서 끝난다. 이 프로젝트는 LG디스플레이 생산 테크니션 3년 경험에서 나온 **현장 도메인 지식**이 기능 하나하나에 박혀 있다.

| 현장 경험 | 시스템 반영 |
|---|---|
| PM(예방정비)/BM(고장정비) 구분, PM 주기 관리 | 점검 유형 분리, PM 스케줄 자동 생성, PM 지연 경고 |
| 설비 상태 관리 (RUN / IDLE / DOWN / PM) | 설비 상태 머신 + 상태별 가동 시간 집계 |
| 알람 코드 체계, 인터락 개념 | 알람 코드 마스터, 심각도(경고/중대/치명) 등급 |
| 교대조(주/야) 인수인계 문화 | 점검 이력에 교대조 필드, 교대별 리포트 |
| MTBF/MTTR/가동률 같은 설비 KPI | KPI 자동 계산 대시보드 |
| 고장 발생 → 조치 → 보고서 작성의 반복 노동 | **AI가 이력+센서 데이터로 고장 리포트 초안 자동 생성** |
| 4M(Man/Machine/Material/Method) 변경 관점 | 고장 원인 분류 체계에 4M 반영 |

핵심 메시지(면접용): *"보고서 쓰느라 야근하던 테크니션이, 그 보고서를 자동으로 써주는 시스템을 직접 만들었다."*

**정직한 한계(자체 인지)**: 위 표는 포트폴리오 **서사(narrative)의 차별점**이지, 사업으로서의 경쟁 우위(moat)는 아니다. 상태머신+CRUD+AI 리포트(Claude API 래핑)는 숙련 개발자가 단기간에 복제 가능한 구조이고, 기존 경량 CMMS(UpKeep/Fiix/MaintainX 등)와 국내 스마트공장 공급기업들이 이미 유사 기능을 상용화했다. 수익화(08)로 넘어갈 때는 이 차이를 반드시 인지하고 실제 경쟁사 조사부터 선행한다 — "아무도 못 따라 한다"는 면접 답변용 문장이지 시장 진입 전략이 아니다.

## 3. 타겟 사용자 (페르소나)

| 페르소나 | 역할 | 핵심 니즈 |
|---|---|---|
| 테크니션 (나의 과거) | 현장 점검·조치 수행 | 점검 입력이 빨라야 함(현장은 바쁨), 모바일/태블릿 대응 |
| 설비 엔지니어 | 고장 분석·PM 계획 | 이력 검색, 센서 트렌드, 고장 리포트, KPI |
| 파트장/관리자 | 라인 전체 현황 파악 | 대시보드 한 화면, 알람 요약, 교대 리포트 |

## 4. 핵심 기능 3축 (MVP)

1. **설비 점검 이력 관리** — 설비 마스터(라인>공정>설비 계층), PM/BM 이력 등록, 체크리스트, PM 스케줄, 교대조 기록
2. **센서 데이터 대시보드** — 시뮬레이터가 생성하는 온도·진동·압력·전류 데이터를 SSE로 실시간 표시, 임계치 초과 시 알람 발생
3. **AI 고장 리포트 자동 요약** — 알람 발생 시점의 센서 데이터 + 최근 점검 이력 + 조치 내역을 AI API(Claude)에 전달 → 고장 리포트 초안(현상/추정원인/조치/재발방지) 자동 생성

부가: JWT 인증 + 역할(관리자/엔지니어/테크니션), 설비 KPI(MTBF/MTTR/가동률).

## 5. 시뮬레이터 컨셉 (실제 설비가 없으므로)

디스플레이 공정을 모델로 한 **가상 라인 1개**를 시뮬레이션:
- 라인: `CELL-1라인` / 공정: 합착(Lami) → 절단(Scribe) → 검사(AOI) 등 3~5개 설비
- 센서: 설비당 온도(℃)·진동(mm/s)·압력(kPa)·전류(A) 4종
- 정상 패턴: 평균±노이즈, 설비별 상이한 기준값
- 이상 시나리오 주입 기능: ① 점진적 드리프트(베어링 마모형) ② 스파이크(순간 과부하) ③ 단차 변화(부품 교체 후 이상) — **현장에서 실제로 보던 고장 전조 패턴을 재현**하는 것이 포인트

## 6. 성공 기준

- [ ] 배포된 데모 URL + 시연 시나리오(정상 → 이상 주입 → 알람 → AI 리포트 생성)가 3분 안에 돌아간다
- [ ] README에 현장 경험 → 기능 매핑 스토리가 담겨 있다
- [ ] 이력서/면접에서 "왜 이 기능을 이렇게 만들었나"에 전부 현장 근거로 답할 수 있다
- [ ] 멀티테넌트 확장 포인트가 코드/DB 설계에 주석으로 남아 있다 (수익화 대비)

## 7. 범위 제외 (1개월 MVP에서 안 하는 것)

- 실제 PLC/설비 연동(OPC-UA, Modbus) — 로드맵 2단계로 문서화만
- 생산 실적/자재/품질 등 MES 타 모듈
- 모바일 네이티브 앱 (반응형 웹으로 대체)
- ML 기반 이상탐지 모델 자체 학습 (임계치 + AI API 요약으로 대체, 확장 여지만 설계)
- 다국어, 결제, 멀티테넌시 실구현
