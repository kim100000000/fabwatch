## F-1 인증 (JWT)

### 규칙
- 로그인: 이메일+비밀번호 → Access(30분) + Refresh(14일) 발급. Refresh는 DB 저장(로그아웃 시 무효화).
- 모든 API는 `Authorization: Bearer` 필수 (로그인/리프레시 제외). 역할 검증은 Spring Security `@PreAuthorize`.
- 비밀번호: BCrypt, 8자 이상 + 영문/숫자 포함.

### 예외
| 케이스 | 처리 |
|---|---|
| 비밀번호 5회 연속 실패 | 15분 잠금 (429 반환) |
| 만료된 Access | 401 + 코드 `TOKEN_EXPIRED` → 프론트가 자동 리프레시 |
| 비활성화 사용자 로그인 | 403 `USER_DISABLED` |

## F-2 설비 마스터

### 계층 구조
```
Line (예: CELL-1라인)
 └─ Process (예: 합착, 절단, 검사)
     └─ Equipment (예: LAMI-01, SCRB-01, AOI-01)
```

### 설비 필드
설비코드(고유, 예 `LAMI-01`), 설비명, 공정, 모델명, 제조사, 설치일, 상태(RUN/IDLE/DOWN/PM), 담당 엔지니어, 비고.

### 상태 머신 (현장 규칙 그대로)
```
RUN ↔ IDLE            (수동 전환)
RUN/IDLE → DOWN       (CRITICAL 알람 자동 or 수동 고장 보고)
DOWN → IDLE           (수리 완료 → 시운전 대기. 사유 필수, 전 역할 가능)
DOWN → RUN            (시운전 생략 복귀. 사유 필수, ENGINEER 이상만)
DOWN → PM             (정비 병행 정기 PM 착수 시 수동)
PM → IDLE             (정비 완료 → 시운전 대기. 바로 RUN 불가가 현장 원칙)
RUN/IDLE → PM         (정기 PM 착수)
```
- **DOWN = BM(계획 외 정지)**: DOWN은 고장 수리 상태다. 수리를 위해 PM으로 바꿀 필요 없이 DOWN에서 바로 조치하고 IDLE로 복귀한다. PM은 계획된 정지(예방보전) 전용이며, 고장 수리가 PM 통계에 섞이지 않게 한다(SEMI E10의 계획/계획외 정지 구분). 화면 표기는 "DOWN (BM)".
- `DOWN → IDLE`/`DOWN → RUN`은 `reason`(사유) 필수 — 비어 있으면 400 `VALIDATION_ERROR`. `DOWN → RUN`은 시운전을 생략한 복귀라 TECHNICIAN은 불가(403 `FORBIDDEN`), 별도 컬럼 없이 상태 로그의 `DOWN → RUN` 전이 자체가 "시운전 생략" 표시가 된다.
- BM 점검 이력(F-3)과의 연결 강제(DOWN 이탈 시 BM 이력 필요)는 F-3 구현 이후 단계에서 도입한다. 지금은 사유만 필수.
- 상태 변경은 전부 `equipment_status_log`에 기록 (이 로그가 KPI 계산의 원천).
- 허용되지 않는 전환 요청 → 400 `INVALID_STATUS_TRANSITION`.
- **범위 한정(중요)**: `RUN/IDLE → DOWN` 자동 전환은 DB `equipment.status` 필드값만 바꾸는 것이며, 실제 설비를 정지시키는 물리적 제어(PLC/Modbus 출력 등)가 절대 아니다. 실제 설비를 제어하는 인터락으로 확장하려면 기능안전 인증(IEC 61508 등) 검토가 선행되어야 한다 — docs/11 §10, docs/07 "다음 단계" 참조.

### 임계치 설정 (센서별)
- warn_low / warn_high / crit_low / crit_high 4개 값. `crit_low ≤ warn_low < warn_high ≤ crit_high` 검증.
- 변경 시 이력 남김 (누가 언제 왜 — 현장에서 임계치 임의 변경은 사고의 씨앗).

## F-3 점검 이력 (핵심 1)

### 3.1 점검 이력 등록
**입력**: 설비, 유형(PM/BM), 교대조(D/N), 시작/종료 일시, 작업자(로그인 사용자 기본), 내용, 조치 사항, (BM일 때) 4M 원인 분류 + 상세 원인, 연계 알람 ID(선택), (PM일 때) 체크리스트 결과.

**비즈니스 규칙**
- 종료일시 > 시작일시. 소요시간 자동 계산(분).
- BM 등록 규칙: 4M 분류 필수. 연계 알람이 있으면 해당 알람 상태를 자동 `RESOLVED` 처리.
- BM 완료 등록 시 설비 상태가 DOWN이면 "정비 완료 → IDLE 전환" 여부를 묻는다(자동 전환 아님 — 현장에선 시운전 확인 후 전환).
- PM 등록 시 해당 설비의 PM 스케줄 `last_done_at` 갱신 → 다음 예정일 재계산.
- 미래 시각 입력 불가. 소요시간 24시간 초과 시 경고(입력은 허용 — 대수리 존재).

### 3.2 PM 체크리스트
- 설비별 템플릿: 항목명, 판정 기준, 순서. (예: LAMI-01 → "롤러 마모 확인: 마모선 이내", "진공 압력: −95kPa 이하", "클린룸 파티클 체크")
- 점검 시 항목별 OK / NG / NA + 메모. **NG가 1건이라도 있으면 이력에 NG 플래그** → 목록에서 붉은 표시, 엔지니어 확인 대상.

### 3.3 PM 스케줄
- 설비별 주기 설정: DAILY / WEEKLY(요일 지정) / MONTHLY(일자 지정).
- `next_due_at` = last_done_at 기준 재계산 (KST 달력 기준, 시각은 last_done 유지: DAILY +1일 / WEEKLY 수행일 이후 첫 해당 요일 / MONTHLY 수행일 이후 첫 해당 일자 — `PmScheduleCalculator`). 예정일 경과 시 상태 `OVERDUE` → 대시보드에 경고 배지.
- OVERDUE 3일 초과 시 MAJOR 알람 자동 생성 ("PM 지연" 유형) — PM 미루다 설비 죽는 현장 패턴 반영.
- PM 수행 시 해당 설비의 미해결 PM 지연 알람은 자동 해소된다 (PM 점검 이력 등록 → 스케줄 갱신과 같은 트랜잭션에서 OPEN/ACK `PM_OVERDUE` 알람을 작성자 명의로 ACK→RESOLVED. 소급 등록으로 스케줄이 갱신되지 않으면 해소하지 않음).

### 3.4 검색/필터
설비, 기간, 유형, 교대조, 작업자, NG 여부. 기본 정렬 최신순, 20건 페이징.

## F-4 센서 시뮬레이터

### 4.1 가상 라인 초기 데이터 (시드)
| 설비 | 공정 | 센서 기준값 (평균/노이즈σ) |
|---|---|---|
| LAMI-01 (합착기) | 합착 | 온도 45℃/0.8, 진동 2.0mm/s /0.3, 압력 −95kPa/1.5, 전류 12A/0.5 |
| LAMI-02 (합착기) | 합착 | 동일 계열, 평균 소폭 상이 |
| SCRB-01 (스크라이버) | 절단 | 온도 38℃/0.6, 진동 3.5mm/s /0.4, 압력 500kPa/8, 전류 8A/0.4 |
| AOI-01 (검사기) | 검사 | 온도 30℃/0.4, 진동 0.8mm/s /0.15, 압력 —, 전류 5A/0.3 |
| OVEN-01 (경화로) | 합착 | 온도 120℃/1.5, 진동 1.0mm/s /0.2, 압력 —, 전류 20A/1.0 |

### 4.2 생성 로직
- `@Scheduled(fixedRate = 2000)`: 설비×센서별 `평균 + N(0,σ)` 생성 → DB 저장 + SSE 발행 + 임계치 판정.
- 활성 시나리오가 있으면 해당 센서에 변형 적용:
  - **DRIFT**: `value += slope × 경과초` (기본 10분에 걸쳐 warn→crit 도달하는 기울기)
  - **SPIKE**: 지정 확률(기본 10%)로 `value × 1.5~2.0`
  - **STEP**: 즉시 `value += offset` 고정 (부품 교체 후 기준선 틀어짐 재현)
- 시나리오는 설비+센서 단위로 주입/해제. 동시 복수 가능.

### 4.3 임계치 판정 → 알람
- warn 초과 → WARNING, crit 초과 → CRITICAL. (MAJOR는 PM 지연 등 시스템 규칙 알람용)
- **중복 억제**: 동일 설비+센서+심각도의 미해결 알람이 있으면 신규 생성 안 함 (알람 폭주는 현장에서 최악 — 실제 알람 무시 문화의 원인).
- CRITICAL 생성 시 설비 상태 자동 DOWN + 상태 로그 기록.

## F-5 실시간 대시보드 (핵심 2)

### 5.1 라인 현황 (메인)
- 설비 카드 그리드: 상태 색(RUN 초록/IDLE 회색/DOWN 빨강/PM 파랑), 현재 센서 4값, 미조치 알람 수 배지, PM OVERDUE 배지.
- 하단: 최근 알람 10건 스트림 (실시간 추가).

### 5.2 설비 상세
- 실시간 차트: 센서별 최근 5분 (SSE 수신, 최대 150포인트 슬라이딩). 임계치 기준선 표시.
- 이력 차트: 기간 선택(1시간/24시간/7일). 24시간 이상은 1분 집계 테이블 사용.
- 탭: 센서 / 점검 이력 / 알람 / 리포트.

### 5.3 알람 흐름
```
OPEN(발생) → ACK(확인, 담당자 기록) → RESOLVED(조치 완료, BM 연계 or 수동 해제)
```
- ACK 없이 RESOLVED 불가. RESOLVED 시 해제 사유 필수.
- SSE로 신규 알람 푸시 → 토스트 + 사운드(옵션).

### 5.4 KPI 계산 (status_log 기반)
- MTBF = Σ(RUN 시간) / DOWN 전환 횟수. DOWN 0회면 "고장 없음" 표시(0으로 나누기 방지).
- MTTR = Σ(DOWN 진입 ~ DOWN 이탈 시각) / DOWN 횟수. 이탈 후 상태(IDLE/RUN/PM)와 무관하게 동일하게 계산한다. 아직 DOWN 중인 건은 제외.
- 가동률 = RUN / (전체 − PM). 기간: 오늘/이번 주/이번 달.

## F-6 AI 고장 리포트 (핵심 3)

### 6.1 생성 흐름
```
[알람 상세 or BM 이력]에서 "AI 리포트 생성" 클릭
→ 백엔드가 컨텍스트 수집:
   ① 알람 정보 (설비, 센서, 심각도, 발생 시각, 당시 값/임계치)
   ② 센서 데이터 요약: 발생 전 30분~후 10분 (1분 집계: min/max/avg 추이 — 원본을 다 보내지 않는다, 토큰 절약)
   ③ 해당 설비 최근 점검 이력 5건 (PM NG 항목 포함)
   ④ 해당 설비 최근 BM 3건 (재발 판단용)
   ⑤ 4M 분류 (BM에 입력된 경우)
→ 프롬프트 조립 → Claude API 호출 (max_tokens 4096 제한, effort low)
→ 마크다운 리포트 초안 저장 (status: DRAFT)
```

### 6.2 리포트 출력 구조 (프롬프트로 강제)
```markdown
# 고장 리포트 — [설비코드] [발생일시]
## 1. 현상 요약        (무엇이, 언제, 어떤 값으로)
## 2. 센서 데이터 분석  (전조 유무 — 드리프트였는지 급발이었는지)
## 3. 추정 원인 (4M)   (가능성 순위 + 근거)
## 4. 권장 조치        (즉시 조치 / 후속 조치 구분)
## 5. 재발 방지 제안   (PM 항목 추가, 임계치 조정, 주기 단축 등)
```
- 시스템 프롬프트에 페르소나 부여: "당신은 디스플레이 제조 설비 엔지니어다. 데이터에 없는 내용을 단정하지 말고 '추정'임을 명시하라."

### 6.3 확정 흐름
- DRAFT → 사용자가 에디터에서 수정 → CONFIRMED 저장. **AI 원본(draft_content)과 확정본(final_content) 별도 보관** (AI를 그대로 믿지 않는다는 설계 근거, 면접 어필 포인트).

### 6.4 예외
| 케이스 | 처리 |
|---|---|
| API 타임아웃(60초) / 5xx | 1회 재시도 → 실패 시 status FAILED + 사유 저장, "수동 작성" 버튼 제공 |
| 429 (rate limit) | 재시도 없이 안내 "잠시 후 다시 시도" |
| 컨텍스트에 센서 데이터 없음 (센서 미부착 설비) | 이력만으로 생성, 리포트에 "센서 데이터 없음" 명시 |
| 일일 생성 한도(기본 20건) 초과 | 403 `AI_QUOTA_EXCEEDED` (데모 비용 보호) |

### 6.5 교대 인수인계 요약 (Should)
- 교대(D/N) 종료 시점 기준: 해당 교대의 알람/점검/상태변경을 모아 5줄 요약 생성. "오늘 야간조에게: LAMI-01 진동 상승 추세 관찰 필요" 같은 현장 어투.

## F-7 공통 규칙

- 모든 시각은 서버 UTC 저장, 화면 KST 표시. 교대 판정: D = 08:00~20:00 KST, N = 20:00~08:00.
- 에러 응답 포맷 통일: `{ "code": "ERROR_CODE", "message": "...", "timestamp": ... }`
- 삭제는 전부 soft delete(deleted_at) — 이력 시스템에서 물리 삭제는 금기.
- 코드 주석 한국어. 멀티테넌트 전환 지점에 `// TENANT:` 주석.
