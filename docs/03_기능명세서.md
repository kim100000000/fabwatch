## F-1 인증 (JWT)

### 규칙
- 로그인: 이메일+비밀번호 → Access(30분) + Refresh(14일) 발급. Refresh는 DB 저장(로그아웃 시 무효화).
- 모든 API는 `Authorization: Bearer` 필수 (로그인/리프레시 제외). 역할 검증은 Spring Security `@PreAuthorize`.
- 비밀번호: BCrypt, 8자 이상 + 영문/숫자 포함.

### 예외
| 케이스 | 처리 |
|---|---|
| 비밀번호 5회 연속 실패 | 15분 잠금 (429 반환) |
| 만료된 Access | 401 + 코드 `TOKEN_EXPIRED` → 프론트가 자동 리프레시 |
| 비활성화 사용자 로그인 | 403 `USER_DISABLED` |

## F-2 설비 마스터

### 계층 구조
```
Line (예: CELL-1라인)
 └─ Process (예: 합착, 절단, 검사)
     └─ Equipment (예: LAMI-01, SCRB-01, AOI-01)
```

### 설비 필드
설비코드(고유, 예 `LAMI-01`), 설비명, 공정, 모델명, 제조사, 설치일, 상태(RUN/IDLE/DOWN/PM), 담당 엔지니어, 비고.

### 상태 머신 (현장 규칙 그대로)
```
RUN ↔ IDLE            (수동 전환)
RUN/IDLE → DOWN       (CRITICAL 알람 자동 or 수동 고장 보고 — 수동 보고는 전 역할 가능한 *현장 고장 보고*이며 상태 전이 권한 우회가 아니다)
DOWN → IDLE           (수리 완료 → 시운전 대기. 사유 필수, 전 역할 가능)
DOWN → RUN            (시운전 생략 복귀. 사유 필수, ENGINEER 이상만)
DOWN → PM             (정비 병행 정기 PM 착수 시 수동)
PM → IDLE             (정비 완료 → 시운전 대기. 바로 RUN 불가가 현장 원칙)
RUN/IDLE → PM         (정기 PM 착수)
```
- **현장 고장 보고 = 자동 DOWN (의도된 설계)**: `POST /alarms/manual`은 전 역할(TECHNICIAN 포함)이 쓸 수 있고, 심각도 CRITICAL로 보고하면 설비가 자동 DOWN 된다. 설비 이상을 가장 먼저 아는 사람은 현장 작업자이므로 "설비 상태 변경 권한"과 별개로 "고장을 알리는 행위"를 허용한 것이다(상태 로그에는 시스템 전환으로 기록, DOWN 복귀는 사유 필수 + 권한 규칙 적용). 자동 DOWN 사유(알람 메시지 포함)는 `status_log.reason` 한도(200자)에 맞춰 말줄임표로 잘린다.
- **DOWN = BM(계획 외 정지)**: DOWN은 고장 수리 상태다. 수리를 위해 PM으로 바꿀 필요 없이 DOWN에서 바로 조치하고 IDLE로 복귀한다. PM은 계획된 정지(예방보전) 전용이며, 고장 수리가 PM 통계에 섞이지 않게 한다(SEMI E10의 계획/계획외 정지 구분). 화면 표기는 "DOWN (BM)".
- `DOWN → IDLE`/`DOWN → RUN`은 `reason`(사유) 필수 — 비어 있으면 400 `VALIDATION_ERROR`. `DOWN → RUN`은 시운전을 생략한 복귀라 TECHNICIAN은 불가(403 `FORBIDDEN`), 별도 컬럼 없이 상태 로그의 `DOWN → RUN` 전이 자체가 "시운전 생략" 표시가 된다.
- BM 점검 이력(F-3)과의 연결 강제(DOWN 이탈 시 BM 이력 필요)는 F-3 구현 이후 단계에서 도입한다. 지금은 사유만 필수.
- 상태 변경은 전부 `equipment_status_log`에 기록 (이 로그가 KPI 계산의 원천).
- 허용되지 않는 전환 요청 → 400 `INVALID_STATUS_TRANSITION`.
- **범위 한정(중요)**: `RUN/IDLE → DOWN` 자동 전환은 DB `equipment.status` 필드값만 바꾸는 것이며, 실제 설비를 정지시키는 물리적 제어(PLC/Modbus 출력 등)가 절대 아니다. 실제 설비를 제어하는 인터락으로 확장하려면 기능안전 인증(IEC 61508 등) 검토가 선행되어야 한다 — docs/11 §10, docs/07 "다음 단계" 참조.

### 임계치 설정 (센서별)
- warn_low / warn_high / crit_low / crit_high 4개 값. `crit_low ≤ warn_low < warn_high ≤ crit_high` 검증.
- 변경 시 이력 남김 (누가 언제 왜 — 현장에서 임계치 임의 변경은 사고의 씨앗).

## F-3 점검 이력 (핵심 1)

### 3.1 점검 이력 등록
**입력**: 설비, 유형(PM/BM), 교대조(D/N), 시작/종료 일시, 작업자(로그인 사용자 기본), 내용, 조치 사항, (BM일 때) 4M 원인 분류 + 상세 원인, 연계 알람 ID(선택), (PM일 때) 체크리스트 결과.

**비즈니스 규칙**
- 종료일시 > 시작일시. 소요시간 자동 계산(분).
- BM 등록 규칙: 4M 분류 필수. 연계 알람이 있으면 해당 알람 상태를 자동 `RESOLVED` 처리.
- BM 완료 등록 시 설비 상태가 DOWN이면 "정비 완료 → IDLE 전환" 여부를 묻는다(자동 전환 아님 — 현장에선 시운전 확인 후 전환).
- PM 등록 시 해당 설비의 PM 스케줄 `last_done_at` 갱신 → 다음 예정일 재계산.
- 미래 시각 입력 불가. 소요시간 24시간 초과 시 경고(입력은 허용 — 대수리 존재).

### 3.2 PM 체크리스트
- 설비별 템플릿: 항목명, 판정 기준, 순서. (예: LAMI-01 → "롤러 마모 확인: 마모선 이내", "진공 압력: −95kPa 이하", "클린룸 파티클 체크")
- 점검 시 항목별 OK / NG / NA + 메모. **NG가 1건이라도 있으면 이력에 NG 플래그** → 목록에서 붉은 표시, 엔지니어 확인 대상.

### 3.3 PM 스케줄
- 설비별 주기 설정: DAILY / WEEKLY(요일 지정) / MONTHLY(일자 지정).
- `next_due_at` = last_done_at 기준 재계산 (KST 달력 기준, 시각은 last_done 유지: DAILY +1일 / WEEKLY 수행일 이후 첫 해당 요일 / MONTHLY 수행일 이후 첫 해당 일자 — `PmScheduleCalculator`). 예정일 경과 시 상태 `OVERDUE` → 대시보드에 경고 배지.
- OVERDUE 3일 초과 시 MAJOR 알람 자동 생성 ("PM 지연" 유형) — PM 미루다 설비 죽는 현장 패턴 반영.
- **PM 이력 종료 시각 수정 시 스케줄 재계산 (M-11)**: `PUT /inspections/{id}`로 PM의 `endedAt`을 바꾸면, 그 이력이 스케줄의 **마지막 수행**(`last_done_at == 수정 전 endedAt`)이었거나 수정 후 `endedAt`이 `last_done_at`보다 **늦어져 새 마지막 수행**이 되는 경우에만 스케줄을 다시 계산한다(마지막 수행과 무관한 과거 이력 수정은 영향 없음, 스케줄 없는 설비·BM·종료 시각이 안 바뀐 수정도 건너뜀). 새 `last_done_at` = 그 설비 PM 이력 중 **가장 늦은 `endedAt`**(수정 반영 후) — 따라서 앞당겨 되돌려도 **직전 PM 수행 시각까지만** 가능하다(생성 시 "소급 등록은 스케줄을 되돌리지 않는다"와 일관). `next_due_at`을 재계산하고 `overdue_alarm_sent=false`로 초기화한다. 수행 시각이 **늦춰진** 경우에는 등록 때와 같이 미해결 `PM_OVERDUE` 알람을 자동 해소하고, 앞당겨진 경우에는 알람을 새로 만들지 않는다(다음 지연 배치가 판정).
- **PM 지연 배치의 스케줄 단위 격리 (M-11)**: 스케줄마다 별도 트랜잭션에서 "최신 상태 재조회 → `PmOverdueEvent` 발행 → `overdue_alarm_sent=true`"를 처리한다. 한 건이 실패해도 그 건(알람+플래그)만 롤백되어 다음 주기에 재시도되고 나머지는 정상 처리된다(실패는 스케줄 ID·예외 클래스만 WARN).
- PM 수행 시 해당 설비의 미해결 PM 지연 알람은 자동 해소된다 (PM 점검 이력 등록 → 스케줄 갱신과 같은 트랜잭션에서 OPEN/ACK `PM_OVERDUE` 알람을 작성자 명의로 ACK→RESOLVED. 소급 등록으로 스케줄이 갱신되지 않으면 해소하지 않음).

### 3.4 검색/필터
설비, 기간, 유형, 교대조, 작업자, NG 여부. 기본 정렬 최신순, 20건 페이징.

## F-4 센서 시뮬레이터

### 4.1 가상 라인 초기 데이터 (시드)

|---|---|---|
| LAMI-01 (합착기) | 합착 | 온도 45℃/0.8, 진동 2.0mm/s /0.3, 압력 −95kPa/1.5, 전류 12A/0.5 |
| LAMI-02 (합착기) | 합착 | 동일 계열, 평균 소폭 상이 |
| SCRB-01 (스크라이버) | 절단 | 온도 38℃/0.6, 진동 3.5mm/s /0.4, 압력 500kPa/8, 전류 8A/0.4 |
| AOI-01 (검사기) | 검사 | 온도 30℃/0.4, 진동 0.8mm/s /0.15, 압력 —, 전류 5A/0.3 |
| OVEN-01 (경화로) | 합착 | 온도 120℃/1.5, 진동 1.0mm/s /0.2, 압력 —, 전류 20A/1.0 |

### 4.2 생성 로직
- `@Scheduled(fixedRate = 2000)`: 설비×센서별 `평균 + N(0,σ)` 생성 → **DB 저장(한 트랜잭션, 먼저 커밋)** → 커밋 이후 SSE 발행 + 임계치 판정(센서별 오류 격리). 상세 트랜잭션 경계는 docs/15 §5.1.
- 활성 시나리오가 있으면 해당 센서에 변형 적용:
  - **DRIFT**: `value += slope × min(경과초, durationMin×60)` (기본 10분에 걸쳐 목표값에 도달하는 기울기). **상한(plateau)**: `durationMin` 경과 후에는 목표값(crit_high **+ 센서 노이즈 1σ**, 없으면 warn_high → crit_low − 1σ → warn_low 순)에서 고정 — crit에 정확히 맞추면 노이즈 때문에 plateau에서 '초과' 판정이 샘플당 약 50%뿐이라 CRITICAL이 안 나올 수 있어 1σ 더 넘긴다되어 시나리오를 해제하지 않아도 값이 무한 상승하지 않는다(노이즈는 유지). 주입 시점에 `slopePerSec`·`maxElapsedSec`(=durationMin×60)·`targetValue`를 param에 굳혀 저장하므로 이후 임계치가 바뀌어도 진행 중 시나리오 거동은 변하지 않는다.
  - **데모 자동 시작(FR-4.5, `POST /simulator/demo`)**: 진동 센서에 DRIFT를 거는데 `durationMin`은 설정 `fabwatch.simulator.demo-duration-min`(환경변수 `SIMULATOR_DEMO_DURATION_MIN`, **기본 2분**) — 정상 → 드리프트 → WARNING → CRITICAL → 자동 DOWN이 3분 시연 안에 일어난다. 이미 DRIFT가 주입돼 있으면 그대로 두고 현재 목록만 반환.
  - **SPIKE**: 지정 확률(기본 10%)로 `value × 1.5~2.0`
  - **STEP**: 즉시 `value += offset` 고정 (부품 교체 후 기준선 틀어짐 재현)
- 시나리오는 설비+센서 단위로 주입/해제. 동시 복수 가능.
- **자동 만료 (안정성 감사 M-13)**: 사용자가 해제하지 않아도 시나리오는 스스로 꺼진다 — 안 그러면 알람을 해제하고 DOWN→IDLE로 복구해도 plateau 값이 2초 안에 CRITICAL을 다시 만들어 알람·자동 DOWN이 재발하고, 서버를 재시작해도 `active=true`가 DB에 남아 복원된다. 만료 시각은 시작 시각 기준:
  - **DRIFT**: `maxElapsedSec`(없는 과거 시나리오는 `durationMin×60`) **+ plateau 유지 시간** `fabwatch.simulator.plateau-hold-minutes`(환경변수 `SIMULATOR_PLATEAU_HOLD_MIN`, 기본 5분). 상한 정보가 아예 없으면 최대 수명.
  - **STEP/SPIKE**: 최대 수명 `fabwatch.simulator.max-lifetime-minutes`(`SIMULATOR_MAX_LIFETIME_MIN`, 기본 30분).
  - 만료 판정은 매 수집 틱에서 한다(경과 시간 ≥ 수명이면 만료). 만료되면 `active=false`, `ended_at`=만료 시각으로 저장하고 INFO 로그 1줄 — 그 틱부터 정상값이 나온다. 재시작 후 복원된 오래된 시나리오도 첫 틱에 정리된다. 사용자의 수동 해제(`DELETE /simulator/scenarios/{id}`)는 그대로다.

### 4.3 임계치 판정 → 알람
- warn 초과 → WARNING, crit 초과 → CRITICAL. (MAJOR는 PM 지연 등 시스템 규칙 알람용)
- **중복 억제**: 동일 설비+센서+심각도의 미해결 알람이 있으면 신규 생성 안 함 (알람 폭주는 현장에서 최악 — 실제 알람 무시 문화의 원인).
- CRITICAL 생성 시 설비 상태 자동 DOWN + 상태 로그 기록. **알람 저장과 자동 DOWN은 한 트랜잭션**(센서 이벤트마다 새 트랜잭션)이라 함께 커밋/롤백된다 — 따로 커밋하면 "알람은 있는데 DOWN은 실패"한 뒤 중복 억제 때문에 DOWN이 영영 재시도되지 않는다. 한 센서의 처리 실패는 다른 센서·저장된 원본에 영향이 없고 다음 틱(2초 뒤)에 재판정된다. 자동 DOWN 상태 로그의 `changed_at`은 전환이 일어난 시각(now)이고 알람 발생 시각은 사유(reason) 끝 `[알람 발생 <UTC ISO>]`에 남는다.
- **상태 전환 동시성 (M-1)**: 수동 전환(`changeStatus`)과 자동 DOWN(`autoDown`)은 설비 행을 `PESSIMISTIC_WRITE`(`SELECT … FOR UPDATE`)로 잠근 뒤 **락 획득 후의 최신 상태**로 전이를 판정한다. 동시에 들어와도 직렬화되어 상태 로그 체인(각 로그의 from == 직전 로그의 to)과 `equipments.status`가 어긋나지 않는다(KPI 오염 방지).

## F-5 실시간 대시보드 (핵심 2)

### 5.1 라인 현황 (메인)
- 설비 카드 그리드: 상태 색(RUN 초록/IDLE 노랑/DOWN 빨강/PM 회색 — docs/04 §1 v1.1), 현재 센서 4값, 미조치 알람 수 배지, PM OVERDUE 배지.
- 하단: 최근 알람 10건 스트림 (실시간 추가).

### 5.2 설비 상세
- 실시간 차트: 센서별 최근 5분 (SSE 수신, 최대 150포인트 슬라이딩). 임계치 기준선 표시.
- 이력 차트: 기간 선택(1시간/24시간/7일). 24시간 이상은 1분 집계 테이블 사용.
- 탭: 센서 / 점검 이력 / 알람 / 리포트.

### 5.3 알람 흐름
```
OPEN(발생) → ACK(확인, 담당자 기록) → RESOLVED(조치 완료, BM 연계 or 수동 해제)
```
- ACK 없이 RESOLVED 불가. RESOLVED 시 해제 사유 필수.
- SSE로 신규 알람 푸시 → 토스트 + 사운드(옵션).

### 5.4 KPI 계산 (status_log 기반)
- **기간**: 오늘(DAY) = 오늘 KST 00:00 ~ now / 이번 주(WEEK) = 이번 주 월요일 KST 00:00 ~ now / 이번 달(MONTH) = 이번 달 1일 KST 00:00 ~ now. DB·API 시각은 UTC지만 **경계는 KST 달력 기준**으로 계산해 UTC로 변환한다(UTC↔KST 9시간 차로 UTC 날짜가 다른 로그에 주의).
- **구간 해석**: 기간 시작 시점 상태 = 시작 시각 이하 마지막 로그의 to_status. 기간에 걸친 구간은 **기간 내로 절삭**, 현재 진행 중 구간은 now까지. 로그가 전혀 없거나 기간 시작 전 상태를 알 수 없는 구간은 **집계에서 제외**(기간 내 첫 로그 이후부터).
- 가동률 = RUN / (집계 대상 전체 − PM), 0~1 비율. 분모 0이면 null.
- MTBF(시간) = Σ(RUN 시간) / DOWN 진입 횟수. DOWN 0회면 null("고장 없음" 표시는 프론트).
- MTTR(분) = Σ(DOWN 진입 ~ DOWN 이탈) / **완료된** DOWN 건수. 이탈 후 상태(IDLE/RUN/PM)와 무관하게 동일. 아직 DOWN 중인 건(기간 끝까지 이탈 없음)은 제외, 완료 0건이면 null. 기간 시작 전에 진입해 기간 내 이탈한 건은 기간 시작부터 이탈까지로 절삭한 길이로 센다.
- downCount = 기간 내 DOWN **진입** 횟수(자동/수동 모두; 기간 전 진입 건은 제외, 진행 중 건은 포함 — MTBF 분모).
- **요약(라인/전체)**: 설비별 비율의 평균이 아니라 Σ 합산 후 재계산한다(가동률 = ΣRUN / Σ(전체−PM), MTBF = ΣRUN / ΣDOWN 진입, MTTR = ΣDOWN 시간 / Σ완료 건수). 삭제(soft delete)된 설비는 제외.
- 구현: 계산은 순수 함수 `KpiCalculator`(DB·시계 비의존, 단위 테스트), 기간 경계는 `KpiPeriod.startAt(now)`.

## F-6 AI 고장 리포트 (핵심 3)

### 6.1 생성 흐름
```
[알람 상세 or BM 이력]에서 "AI 리포트 생성" 클릭
→ 백엔드가 컨텍스트 수집:
   ① 알람 정보 (설비, 센서, 심각도, 발생 시각, 당시 값/임계치)
   ② 센서 데이터 요약: 발생 전 30분~후 10분 (1분 집계: min/max/avg 추이 — 원본을 다 보내지 않는다, 토큰 절약)
   ③ 해당 설비 최근 점검 이력 5건 (PM NG 항목 포함)
   ④ 해당 설비 최근 BM 3건 (재발 판단용)
   ⑤ 4M 분류 (BM에 입력된 경우)
→ 프롬프트 조립 → Claude API 호출 (max_tokens 4096 제한, effort low)
→ 마크다운 리포트 초안 저장 (status: DRAFT)
```

### 6.2 리포트 출력 구조 (프롬프트로 강제)
```markdown
# 고장 리포트 — [설비코드] [발생일시]
## 1. 현상 요약        (무엇이, 언제, 어떤 값으로)
## 2. 센서 데이터 분석  (전조 유무 — 드리프트였는지 급발이었는지)
## 3. 추정 원인 (4M)   (가능성 순위 + 근거)
## 4. 권장 조치        (즉시 조치 / 후속 조치 구분)
## 5. 재발 방지 제안   (PM 항목 추가, 임계치 조정, 주기 단축 등)
```
- 시스템 프롬프트에 페르소나 부여: "당신은 디스플레이 제조 설비 엔지니어다. 데이터에 없는 내용을 단정하지 말고 '추정'임을 명시하라."

### 6.3 확정 흐름
- DRAFT → 사용자가 에디터에서 수정 → CONFIRMED 저장. **AI 원본(draft_content)과 확정본(final_content) 별도 보관** (AI를 그대로 믿지 않는다는 설계 근거, 면접 어필 포인트).

### 6.4 예외
| 케이스 | 처리 |
|---|---|
| API 타임아웃(60초) / 5xx | 1회 재시도 → 실패 시 status FAILED + 사유 저장, "수동 작성" 버튼 제공 |
| 429 (rate limit) | 재시도 없이 안내 "잠시 후 다시 시도" |
| 컨텍스트에 센서 데이터 없음 (센서 미부착 설비) | 이력만으로 생성, 리포트에 "센서 데이터 없음" 명시 |
| 일일 생성 한도(기본 20건) 초과 | 403 `AI_QUOTA_EXCEEDED` (데모 비용 보호) |

### 6.5 교대 인수인계 요약 (Should)
- 교대(D/N) 종료 시점 기준: 해당 교대의 알람/점검/상태변경을 모아 5줄 요약 생성. "오늘 야간조에게: LAMI-01 진동 상승 추세 관찰 필요" 같은 현장 어투.

## F-7 공통 규칙

- 모든 시각은 서버 UTC 저장, 화면 KST 표시. 교대 판정: D = 08:00~20:00 KST, N = 20:00~08:00.
- 에러 응답 포맷 통일: `{ "code": "ERROR_CODE", "message": "...", "timestamp": ... }`
- 삭제는 전부 soft delete(deleted_at) — 이력 시스템에서 물리 삭제는 금기.
- 코드 주석 한국어. 멀티테넌트 전환 지점에 `// TENANT:` 주석.
